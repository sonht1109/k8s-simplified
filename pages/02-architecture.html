Kubernetes Architecture

A Kubernetes cluster has a "brain" (the control plane) and "muscle" (the worker nodes). You'll meet every component, learn what each one does, and follow a request from kubectl all the way to a running container.

New here? Lesson 1 explains what Kubernetes is and why we use it.

Learn it by comparing with Docker

Lists of components are easy to forget, so let's derive them. Start with what happens in Docker, then see what Kubernetes needs on top. The four things Kubernetes adds over Docker (Lesson 1) are: a cluster, auto-healing, auto-scaling, and enterprise features like advanced load balancing, security and networking.

Docker. On a machine with Docker, you type docker run and a container starts. Under the hood, a container runtime does the real work. A Java app can't run without a Java runtime; likewise a container can't run without a container runtime.

Kubernetes. The smallest thing you deploy is a Pod, a wrapper around your container with extra abilities (Lesson 4). Your request does not go straight to a worker machine. It always goes through the control plane first. To see why, build up from the worker.

  • Something must keep the Pod running (Docker has an engine for that). In Kubernetes it's the kubelet. Because Kubernetes promises auto-healing, the kubelet also keeps checking "is the Pod running?" and reports back to the control plane if not.
  • Something must run the container. That's the container runtime. In Docker you only get Docker's own. Kubernetes is more open: it defines a standard called the Container Runtime Interface (CRI), so containerd, CRI-O or Docker's runtime can all be used, as long as they implement it.
  • Something must give Pods networking. Docker has its default bridge network. In Kubernetes every Pod needs an IP address, and because of auto-scaling (say, 2 replicas) traffic must be split, "50% here, 50% there." That's kube-proxy: IP addressing plus basic load balancing, using the Linux iptables rules on each node.

Those three (kubelet, kube-proxy, container runtime) form the worker node, also called the data plane. Together they have everything needed to run an app. So why a control plane? Because a cluster with many users and many nodes needs a "heart": someone to decide which node gets the Pod, to receive and secure every request, to remember the cluster's state, and to keep the controllers running. That's the next set of components.

The big picture

A cluster is a group of machines working together. They come in two roles:

  • Control plane (older name: master node): makes the decisions. It stores the cluster's data, decides where Pods run, and reacts to changes.
  • Worker nodes: the machines that actually run your containers.
Think of it like…A restaurant. The manager's office (control plane) takes orders, keeps the books, and assigns tables to waiters. The kitchen and floor staff (worker nodes) cook and serve the food.

SchedulerWatches for new Pods with no node and picks the best node, based on free CPU and memory and any rules you set.
Controller managerKubernetes has built-in controllers, such as the ReplicaSet controller: if your YAML says "2 Pods," it makes sure two are always running (Lesson 5). The controller manager is the program that keeps all these controllers running.
Cloud controller manager (CCM)Only in cloud clusters (EKS, AKS, GKE). When you ask for a load balancer or storage, Kubernetes must turn that into the API call each cloud understands. Kubernetes can't contain logic for every cloud, so the CCM is open source: a brand-new cloud provider can add its own logic to it. On-premises clusters don't need it at all.

kubeletThe agent on every node. It takes the Pods assigned to its node, makes sure they keep running, and reports problems back to the API server so the control plane can act.

Follow a request

Say you run kubectl apply -f app.yaml asking for a new Pod. Step through what happens.

Try it: life of a request

Press Next and watch the highlighted component in the diagram above.

Press Next step to begin.
  1. kubectl to API server. kubectl sends your YAML as an HTTPS request, with your credentials from the kubeconfig file.
  2. API server to etcd. After checking your identity and permissions, the API server stores the new Pod object in etcd. It has no node yet.
  3. Scheduler. It notices a Pod without a node, picks the best one, and records that choice through the API server.
  4. kubelet. The kubelet on the chosen node sees a Pod assigned to it and asks the container runtime to pull the image and start the container.
  5. Status back. The kubelet reports "Running" to the API server, which saves it in etcd. kubectl get pods now shows it.

Afterwards the controller manager keeps watching. If the Pod disappears later and your desired state says it should exist, a controller asks for a new one and the cycle repeats. That loop is the heart of Kubernetes.

Interview angle"What are the components of Kubernetes?" Answer in two groups. Control plane (controls the actions): API server, scheduler, etcd, controller manager, cloud controller manager. Data plane / worker node (executes them): kubelet, kube-proxy, container runtime. Then explain each one's purpose, not just its name. Good practice: write these notes with a diagram of a Pod's creation and share it.

kubectl: your remote control

kubectl is the command-line client for the API server. It reads a kubeconfig file (by default ~/.kube/config) that says which cluster to talk to and as whom.

kubectl version --client       # check the install
kubectl cluster-info           # where is the API server?
kubectl get nodes              # list the machines in the cluster
kubectl get pods -A            # Pods in all namespaces
kubectl config get-contexts    # which clusters can I reach?
TipEven on a managed cluster, the control plane Pods live in the kube-system namespace. Run kubectl get pods -n kube-system to see components such as kube-proxy and CoreDNS (the cluster's DNS server) running.
Interview angle"What happens when you run kubectl apply?" Walk through API server, etcd, scheduler, kubelet, container runtime. Mention that only the API server talks to etcd.

Check yourself

Which component decides which node a new Pod runs on?
The scheduler assigns unscheduled Pods to nodes. The kubelet then runs them.
Where is the cluster's state (all objects and their settings) stored?
etcd is the cluster's database, and only the API server talks to it.
Which component runs on every worker node and makes sure Pods are running as assigned?
The kubelet is the node agent that starts Pods and reports their health.

Key takeaways

  • A cluster = control plane (decides) + worker nodes (run containers).
  • Control plane: API server (front door), etcd (database), scheduler (placement), controller manager (reconcile loops), optional cloud controller.
  • Worker node: kubelet (agent), kube-proxy (networking rules), container runtime (runs containers).
  • Every action goes through the API server; only it talks to etcd.
  • kubectl is just a client that sends requests to the API server using your kubeconfig.
