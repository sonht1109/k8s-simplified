RBAC: Who Can Do What

On your laptop cluster you are the boss. In a company, many people and many apps share one cluster, and each should only touch what they need. RBAC (Role-Based Access Control) is how Kubernetes decides who may do what.

RBAC is enforced by the API server, the front door of the cluster. See Lesson 2: Architecture if you need a refresher on it.

Why RBAC matters

Imagine a cluster shared by developers, QA engineers and DevOps engineers. You do not want a QA engineer deleting things in the kube-system namespace, or a buggy app wiping out Deployments. Because RBAC is directly about security, a small mistake can be both dangerous and hard to debug.

RBAC answers two questions, for two kinds of "callers":

  • Users (humans): what may a developer, a tester or an admin do?
  • Service accounts (programs running in Pods): what may this application do when it talks to the API server?

Authentication comes first, then authorization

Every request to the API server goes through two checks in order:

  1. Authentication asks "Who are you?" (a user, a group or a service account).
  2. Authorization asks "Are you allowed to do this?" RBAC is the most common way to answer.

RBAC only handles step 2. It never proves who you are.

Where do users come from?

This surprises many beginners: Kubernetes has no "create user" command. There is nothing like useradd. Instead, Kubernetes hands user management to an identity provider, just like an app that lets you "Log in with Google" without creating a new account.

  • On EKS, you can map AWS IAM users and groups to Kubernetes.
  • On OpenShift or other platforms, the provider could be LDAP, Okta, GitHub (often through a broker such as Keycloak), or any single sign-on system.
  • The cluster receives the person's username and group names from the provider, and RBAC rules refer to those names.

Service accounts are different: they are Kubernetes objects, and anyone with permission can create one.

Service accounts

A ServiceAccount is an identity for a Pod. When your app calls the API server (to read a ConfigMap, list Pods, and so on), it proves who it is with its service account.

  • Every namespace has a default service account. A Pod that does not name one gets default automatically.
  • For real apps, create a dedicated one with only the permissions that app needs.
apiVersion: v1
kind: ServiceAccount
metadata:
  name: reader-sa
  namespace: dev
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  namespace: dev
spec:
  serviceAccountName: reader-sa
  containers:
  - name: app
    image: nginx

The building blocks

Permissions are built from two ideas: a rule set (what is allowed) and a binding (who gets it).

ObjectScopeWhat it does
RoleOne namespaceLists allowed actions on resources in that namespace
ClusterRoleWhole clusterSame, but also covers cluster-wide resources (like Nodes) or all namespaces
RoleBindingOne namespaceAttaches a Role (or ClusterRole) to users, groups or service accounts in that namespace
ClusterRoleBindingWhole clusterAttaches a ClusterRole to subjects everywhere
Think of it like…A Role is a key card design ("opens the supply room and the printer room"). A RoleBinding is the act of handing that card to a specific person. A key card with nobody holding it opens nothing, and a person with no card opens nothing either. You need both. If you know AWS, a Role is close to an IAM policy.

Writing a Role and a RoleBinding

A Role contains rules. Each rule says which API groups, resources and verbs are allowed. Everything not listed is denied; RBAC has only allow rules.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]          # "" means the core group (Pods, ConfigMaps, Secrets...)
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]

Now bind it to a user and a service account:

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: priya
  apiGroup: rbac.authorization.k8s.io
- kind: ServiceAccount
  name: reader-sa
  namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

Common verbs are get, list, watch, create, update, patch and delete. For a ClusterRole and ClusterRoleBinding, the YAML looks the same: drop namespace and change the kind.

TipA ClusterRole can be reused inside one namespace. Bind it with a RoleBinding and its power is limited to that namespace. Kubernetes' built-in view, edit and admin ClusterRoles are used this way all the time.

Testing permissions with kubectl auth can-i

You do not need to log in as someone to test their access. Ask the API server:

# Can I (the current user) delete deployments in dev?
kubectl auth can-i delete deployments -n dev

# Can user priya list pods in dev? (needs admin rights to impersonate)
kubectl auth can-i list pods -n dev --as priya

# Can the service account read secrets?
kubectl auth can-i get secrets -n dev \
  --as system:serviceaccount:dev:reader-sa

# Everything I may do in a namespace
kubectl auth can-i --list -n dev

The answer is simply yes or no. This is the quickest way to debug a "forbidden" error.

Check yourself

You created a Role that allows listing Pods, but the user still gets "forbidden". What is most likely missing?
A Role only describes permissions. Nobody has them until a RoleBinding links the Role to a subject.
How do you create a human user in Kubernetes?
Kubernetes offloads user management. Only service accounts are created inside the cluster.
Which command checks whether a service account may read Secrets?
auth can-i with --as impersonates the subject and returns yes or no.

Key takeaways

  • RBAC is the authorization step: it decides what an already-identified user or service account may do.
  • Kubernetes does not manage human users; identity providers do. Service accounts are native objects used by Pods.
  • Role (namespace) or ClusterRole (cluster) = the permissions. RoleBinding or ClusterRoleBinding = who gets them.
  • RBAC has only allow rules; anything not granted is denied.
  • Use dedicated service accounts and least privilege; test with kubectl auth can-i.
