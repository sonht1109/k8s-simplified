Deployments & ReplicaSets

A bare Pod can't heal or scale. A Deployment fixes that: you say how many copies you want and which version, and Kubernetes keeps it true, even during updates. You'll learn Deployments, ReplicaSets, scaling, rolling updates and rollbacks.

This lesson builds on Lesson 4: Pods (YAML structure, kubectl basics, labels).

Container vs Pod vs Deployment

This is a classic entry-level interview question, and if you can't answer it, interviewers assume you haven't used Kubernetes. Here is the answer in three steps.

  • Container: you run it with a command like docker run -d -p 80:80 -v ... --network ... image, passing every option on the command line.
  • Pod: Kubernetes' enterprise version of that. The same options go into a YAML manifest, so a Pod manifest is simply the "running specification" of your container(s). A Pod can hold several containers, for example your app plus a sidecar (service meshes use this) that share networking over localhost and share volumes.
  • Deployment: a wrapper on top of Pods that adds what Pods lack: auto-healing, auto-scaling and zero-downtime updates.

A Pod is just a specification for running containers. It has no auto-healing or auto-scaling. So Kubernetes' advice is: don't create Pods directly; create a Deployment. You still learn Pods, because in the end it's Pods that run. (Pods are covered in Lesson 4.)

Why not just use Pods?

Imagine you run an app as a plain Pod and someone deletes it by accident, or its node crashes, or a network problem kills it. The app is gone, and customers who try to reach it find nothing. Docker had the same weakness, so where is the Kubernetes advantage? You get it only by creating the right resource. And if a million users arrive, one Pod isn't enough; you want, say, two or a hundred copies sharing the load.

You need something to watch the Pods and keep the right number alive. That's a controller: a program (Kubernetes' built-in ones are written in Go) whose whole job is to make the actual state of the cluster equal the desired state written in your YAML. Anything that does this is a controller. The controller manager from Lesson 2 runs the built-in ones, and you can add custom ones such as Argo CD (more in Lesson 12).

The chain: Deployment, ReplicaSet, Pods

  • Pod: runs your container.
  • ReplicaSet: a Kubernetes controller that keeps the number of Pods the Deployment asked for. If one disappears, it creates another. This is what actually implements auto-healing.
  • Deployment: a high-level abstraction on top. You create just one resource and it creates the ReplicaSet, which creates the Pods. On its own it does nothing; it hands the work to the ReplicaSet. It also adds updating and rolling back versions.
Think of it like…A shift manager (Deployment) who hires a team lead (ReplicaSet) for each version of the staff handbook. The team lead makes sure exactly 3 workers (Pods) are always on duty. For a new handbook, the manager brings in a new team lead and retires the old one gradually.

Desired state and self-healing

A Deployment's manifest states the desired state: image, number of replicas. Kubernetes constantly compares it with what is running and fixes any difference. That is why a deleted Pod comes back.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.26
          ports:
            - containerPort: 80
  • replicas: how many Pods you want.
  • template: a Pod blueprint (the same metadata + spec you wrote in Lesson 4).
  • selector.matchLabels: which Pods belong to this Deployment. It must match the labels in template.metadata.labels, otherwise the Deployment is rejected.
kubectl apply -f deployment.yaml
kubectl get deployments
kubectl get replicaset
kubectl get pods                     # names look like nginx-deployment-5d9c7b8f4-abcde
kubectl delete pod <one-pod-name>    # watch a replacement appear
kubectl get pods -w                  # -w = keep watching

Everything below is hands-on, so try it. Before you start, check that your cluster is clean: kubectl get all lists the Pods, Deployments, Services and so on in the current namespace, and kubectl get all -A does it for all namespaces.

Notice the Pod names: the Deployment name, then the ReplicaSet's hash, then a random suffix. Delete one and a new name appears within seconds.

Hands-on: see the controller work

Try this on any cluster (minikube is fine). It is the best way to feel what a Deployment gives you.

  1. First, the problem. Create a plain Pod (kubectl apply -f pod.yaml), note its IP with kubectl get pods -o wide, and check it from inside the cluster (on minikube: minikube ssh, then curl POD_IP). It works. Now kubectl delete pod nginx and curl again: the app is gone, and nothing brings it back.
  2. Create a Deployment with replicas: 1 (kubectl apply -f deployment.yaml). Then run kubectl get deploy, kubectl get rs (rs is short for ReplicaSet) and kubectl get pods. You created one resource, and all three exist.
  3. Watch it heal. In one terminal run kubectl get pods -w. In another, delete the Pod. You see the old Pod go Terminating while a new one is already Running; deletion and creation happen in parallel, so the app is never without a Pod.
  4. Scale. Edit replicas: 3 in the file and run kubectl apply -f deployment.yaml again. The ReplicaSet notices the new desired state and creates two more Pods, leaving the existing one untouched. Delete any one and it is replaced, still giving you 3.

That is "zero downtime" in action: changing replicas or losing a Pod never disturbs the Pods that are already serving. (Routing real user traffic to the Pods is the job of Services and Ingress, coming in later lessons.)

Scaling

kubectl scale deployment nginx-deployment --replicas=10
# or edit "replicas:" in the file and run: kubectl apply -f deployment.yaml

Kubernetes creates or removes Pods until the count matches. Scaling can also be automatic with a HorizontalPodAutoscaler, which adds Pods when CPU use rises.

Rolling updates

Change the image in the Deployment, for example nginx:1.26 to nginx:1.27:

kubectl set image deployment/nginx-deployment nginx=nginx:1.27
kubectl rollout status deployment/nginx-deployment

By default the Deployment uses a rolling update: it creates a new ReplicaSet, starts one or a few new Pods, waits until they are ready, then removes old ones, step by step. At every moment some Pods are serving, so users see no downtime. How many may be added or unavailable at once is controlled by maxSurge and maxUnavailable (each defaults to 25%).

Rollback

The old ReplicaSet is kept (scaled to zero), so going back is fast.

kubectl rollout history deployment/nginx-deployment
kubectl rollout undo deployment/nginx-deployment
kubectl rollout undo deployment/nginx-deployment --to-revision=1

More release styles (blue/green, canary) are covered in Lesson 18.

Labels and selectors

The Deployment doesn't track Pods by name. It finds them by label. Any Pod matching app: nginx counts toward the replica number. Good to know: if you hand-create a Pod with that label, the ReplicaSet may count it and delete an extra, and changing a Pod's label removes it from the Deployment's control. Use kubectl get pods --show-labels to check.

Watch outDon't edit or create the ReplicaSet directly. Always change the Deployment; it owns the ReplicaSets and your edits would be lost or fight with it.
Interview angleTwo common questions. (1) "Container vs Pod vs Deployment?" Use the three bullets near the top. (2) "Deployment vs ReplicaSet?" The ReplicaSet is the controller that implements auto-healing by keeping the actual Pod count equal to the desired count; creating a Deployment creates one automatically, and the Deployment adds rollout and rollback on top. Nobody will ask you to write YAML from memory (copy examples from the official docs and change the values). Expect questions like "what is the image field?", "what are labels and selectors for?" and "what do replicas do?"
PracticeTake an example Deployment from the official Kubernetes docs or the official examples repository on GitHub (the guestbook example is a good one), replace the image with your own app, kill Pods, change replicas and watch kubectl get rs. Day-to-day work is Deployments, not bare Pods.

Check yourself

You run a Deployment with 3 replicas and delete one Pod. What happens?
The desired state is 3, the actual is 2, so the controller creates another.
Which command undoes the last rollout?
The previous ReplicaSet is still stored, so Kubernetes switches back to it.
What must spec.selector.matchLabels match?
The selector tells the Deployment which Pods are its own, so it must match the template's labels.

Key takeaways

  • Deployment manages ReplicaSets; a ReplicaSet keeps N identical Pods running.
  • You declare the desired state; controllers keep reality matching it (self-healing).
  • Scale with kubectl scale or by editing replicas.
  • Updates are rolling by default: new Pods start before old ones stop, so there's no downtime.
  • Roll back with kubectl rollout undo; inspect with rollout status and rollout history.
  • Pods are matched by labels, so selector and template labels must agree.
