Real Production Challenges

Three problems almost every DevOps engineer meets on live clusters: teams fighting over shared resources, Pods killed for running out of memory, and cluster upgrades. Knowing how to explain them also makes you sound very credible in interviews.

Challenge 1: sharing one cluster between many teams

In production, teams rarely get a cluster each. Many microservices and project teams deploy to the same cluster, so a DevOps engineer must decide how to split its CPU and memory fairly.

The obvious first step is one namespace per team (for example web, payments, shipping). But namespaces by themselves are only labels and boundaries for names and permissions. They do not limit resource use.

The problemSuppose the cluster has 100 CPU and 100 GB RAM. A service in the payments namespace has a memory leak and starts taking 32 GB instead of 2 GB. Everybody else now has less. Services in other namespaces get starved, crash, and show up as CrashLoopBackOff with OOMKilled. One team's bug becomes everyone's outage.

The term for how far a failure spreads is its blast radius. Your goal is to shrink it, in two steps.

Step 1: ResourceQuota (a cap per namespace)

A ResourceQuota sets a total limit for everything in a namespace. All its Pods together cannot exceed it, whether that is 5 services or 100.

apiVersion: v1
kind: ResourceQuota
metadata:
  name: payments-quota
  namespace: payments
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 10Gi
    limits.cpu: "15"
    limits.memory: 15Gi
    pods: "50"

How do you pick the numbers? Ask each team to do performance benchmarking of their services and tell you what they really need. You can challenge unusual numbers in a meeting, but once the data is sound, you allocate it. If the quotas add up to more than the cluster has, your job is to add nodes.

The blast radius is now one namespace instead of the whole cluster. But inside that namespace, a leaking Pod can still starve its neighbours.

Step 2: resource requests and limits (a cap per container)

Set them on each container. A request is the minimum the scheduler reserves; a limit is the maximum the container may use.

containers:
- name: payment-api
  image: example/payment-api:1.4
  resources:
    requests:
      cpu: "500m"
      memory: 512Mi
    limits:
      cpu: "1"
      memory: 1Gi
  • If a container goes over its memory limit, it is killed (OOMKilled). Only that one Pod suffers.
  • If it goes over its CPU limit, it is slowed down (throttled), not killed.
TipWhen a ResourceQuota covers CPU or memory, every new Pod in that namespace must specify requests and limits, or it is rejected. A LimitRange can set defaults so teams do not forget.

Challenge 2: a Pod keeps getting OOMKilled

You have set the quota and limits, and still one Pod goes into CrashLoopBackOff. Remember that CrashLoopBackOff is only a status. The real reason is shown by describe:

kubectl get pods -n payments
kubectl describe pod <pod> -n payments
#   Last State:  Terminated
#     Reason:    OOMKilled
#     Exit Code: 137

The general debug flow is in Lesson 20: CrashLoopBackOff. Here is the production angle:

  1. Rule out noise. Without quotas and limits, an OOMKill might be caused by another team's greedy Pod. With them in place, the guilty Pod identifies itself.
  2. Check the limit is realistic against the team's benchmarking data. A limit that is too tight kills a healthy app. Raise it if the data supports it.
  3. If it still dies with a sensible limit, the app is leaking. As a DevOps engineer, collect evidence for the developers: a thread dump and heap dump for a Java app (for example with kill -3 or jmap/jstack; other languages have their own profilers), plus metrics from Prometheus and Grafana showing memory over time.
  4. Developers analyze the dumps, find the leak, and ship a new version. You deploy it.
Interview angle"How do you handle OOMKilled?" Describe the order: confirm via describe that it is OOM, check quotas and limits, review memory usage graphs, take dumps, hand them to developers, redeploy the fix. Say that CrashLoopBackOff is a symptom, OOMKilled is the cause.

Challenge 3: upgrades

Kubernetes releases often, so every cluster must eventually move from, say, 1.29 to 1.30. It is risky, since the control plane and every node are touched. Teams that do it well write a manual (a runbook) with the exact steps and rehearse it.

A good manual contains:

  • Backups first: etcd snapshot and a copy of your manifests.
  • Read the release notes. Engineers often skip this. Removed or deprecated APIs and behaviour changes can break your workloads or even the cluster.
  • Control plane first (etcd, API server, scheduler, controller manager), in the documented order.
  • Then the nodes, one at a time: drain a node (Pods move elsewhere), make it unschedulable (cordon), upgrade kubelet and packages, rejoin it, make it schedulable again, and move on to the next node.
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
# ...upgrade kubelet and packages on node-1...
kubectl uncordon node-1

The full procedure, version skew rules and rollback planning are covered in Lesson 16: Upgrading a Cluster in Production. For managing many clusters, see Lesson 3.

How to tell these stories

A reliable way to answer "what challenges have you faced?": state the situation, what went wrong, what you changed, and the result. For example: "A shared cluster was hit by one leaking Pod. I introduced namespace quotas and Pod limits, so the problem now stays inside a single Pod and we can see exactly which one."

Check yourself

Namespaces alone do not stop one team from using all the memory. What does?
ResourceQuota caps the total CPU, memory and object counts a namespace may use.
A container exceeds its memory limit. What happens?
Memory cannot be throttled, so the container is killed. CPU overuse only slows the container down.
During a node upgrade, what do you do before upgrading kubelet on that node?
Drain (which also cordons) moves workloads away safely before the node is touched.

Key takeaways

  • Namespaces separate teams but need a ResourceQuota to cap what each can consume.
  • Set requests and limits on containers so a leaky app only hurts itself. Think "blast radius".
  • CrashLoopBackOff is a status; check describe for the real cause such as OOMKilled.
  • For persistent OOMs, share thread/heap dumps and metrics with developers.
  • Upgrades need backups, release-note review, control plane first, then drain-and-upgrade each node.
