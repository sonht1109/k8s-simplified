Helm: The Package Manager

Helm installs, upgrades and removes whole applications on Kubernetes with one command. You'll learn charts, repositories, releases and values, then build and package a chart of your own.

What is Helm?

Helm is the package manager for Kubernetes. If you know Ubuntu, the idea is the same as apt: instead of hunting for install steps, you run one command and the tool does everything.

Linux (apt)Kubernetes (Helm)
packagechart
repository (archive.ubuntu.com)repository (e.g. Bitnami)
apt install python3helm install my-name repo/chart
upgrade / remove packagehelm upgrade / helm uninstall

Why not just kubectl apply?

You can install anything with kubectl apply, just like you can install anything on Linux with curl and shell scripts. The pain shows up at scale:

  • A tool like Prometheus needs a namespace, a service account, config maps, a Deployment or StatefulSet, Services, and they must be created in the right order.
  • Team A wants version 2.12 and team B wants 2.13. UAT needs 2 replicas, production needs 3. You'd keep copying and editing YAML files and scripts.
  • Those scripts must be tested and kept current as the software changes.

Helm bundles all the YAML into one chart, lets you change settings from outside, and tracks what it installed so it can upgrade or remove it cleanly.

Four words to know

Chart

A package: all the Kubernetes YAML for an app, plus default settings.

Repository

A place that stores and serves charts. helm repo add registers one.

Release

One installed copy of a chart in a cluster, with a name you choose. Install the same chart twice and you get two releases.

Values

The settings you can change (replicas, image tag, resources) without editing the chart.

Install Helm

Helm is a command-line tool on your laptop (brew install helm on macOS, or the installer for your OS from the Helm docs). Nothing is installed in the cluster; Helm 2 needed a server part called Tiller, Helm 3 does not. Like kubectl, Helm talks to whichever cluster is the current context in your kubeconfig.

helm version
kubectl config current-context

Installing third-party apps

Two steps: add the repository once, then install a chart from it.

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo bitnami | grep -i nginx

helm install nginx-v1 bitnami/nginx
helm list
kubectl get pods

In helm install nginx-v1 bitnami/nginx, nginx-v1 is the release name and bitnami/nginx is repo/chart. The release name is required; it lets you install many copies and later upgrade or remove the right one.

Not in Bitnami? Search the project's own docs. Most tools publish their own repo (for example, the AWS Load Balancer Controller documents its eks chart repo). Add it the same way.

NoteHelm is used to install tools like Prometheus and Grafana too. How they work is in Lesson 14.

Values: customising an install

Every chart ships default settings in values.yaml. See what you can change, then override at install time:

helm show values bitnami/nginx
helm install web bitnami/nginx --set replicaCount=3
helm install web2 bitnami/nginx -f my-values.yaml

--set is good for one or two values; -f file.yaml is better for a set you keep in Git (one file per environment).

Upgrade, history, rollback, uninstall

helm upgrade web bitnami/nginx --set replicaCount=5
helm history web
helm rollback web 1
helm uninstall web
  • upgrade changes an existing release (new chart version or new values).
  • Each change is a numbered revision, so rollback returns to an earlier one.
  • uninstall takes the release name and removes everything the chart created.

Build your own chart

You can package your own microservices too. Say you work on a shop with a payments and a shipping service. Let Helm create the skeleton:

helm create payments

Three things matter in the folder:

payments/
  Chart.yaml      # metadata: name, chart version, app version
  values.yaml     # default settings
  templates/      # your YAML files, with placeholders
  charts/         # dependencies (ignore for now)
  • templates/: put your Deployment, Service, ConfigMap etc. here. Replace fixed values with placeholders.
  • values.yaml: the values those placeholders read.
  • Chart.yaml: who owns it, chart version, app version.

A trimmed templates/deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-payments
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}-payments
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-payments
    spec:
      containers:
      - name: payments
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
# values.yaml
replicaCount: 1
image:
  repository: busybox
  tag: latest

The Deployment and its fields are covered in Lesson 5. Here, the only new thing is the {{ }} placeholders.

Try it: values fill the template

Change the values and see the YAML Helm would produce. Think of it as "UAT vs production".

Package and publish

helm package payments        # creates payments-0.1.0.tgz
helm package shipping
helm repo index .            # creates index.yaml listing both charts

Upload the .tgz files and index.yaml to any web location (an artifact server like Nexus or Artifactory, or GitHub Pages). Anyone can then run helm repo add best-commerce <url> and helm install p1 best-commerce/payments, exactly like Bitnami charts.

Helm vs Kustomize

Both solve "same app, different settings". They take different approaches.

HelmKustomize
IdeaTemplates + values, packaged as chartsPlain YAML + patches/overlays
Sharing appsStrong: repositories, versionsNot a package format
LifecycleReleases, upgrade, rollbackJust generates YAML
Learning curveTemplate syntaxGentler

Many teams use Helm to install third-party tools and Kustomize (or Helm values files) for their own apps.

Interview angle"What problem does Helm solve?" Packaging, versioning and configuring many YAML files as one unit, with upgrade and rollback. Be ready to name chart, release, repository and values.

Check yourself

What is a Helm release?
A chart is the package; a release is a named install of it. Install the same chart twice and you have two releases.
You want 3 replicas in production and 2 in UAT, using the same chart. What do you change?
Templates stay the same; values are what change per environment.
How does Helm 3 know which cluster to install into?
Like kubectl, Helm uses your kubeconfig. Helm 3 has no server component.

Key takeaways

  • Helm is a package manager: chart = package, repository = store, release = installed copy, values = settings.
  • Install flow: helm repo add, helm search repo, helm install NAME repo/chart.
  • helm upgrade, helm history, helm rollback, helm uninstall manage the release lifecycle.
  • Use helm show values to see options; override with --set or -f.
  • Your own chart = Chart.yaml + values.yaml + templates/; publish with helm package and helm repo index.
  • Helm packages and shares; Kustomize patches plain YAML. They can be combined.
