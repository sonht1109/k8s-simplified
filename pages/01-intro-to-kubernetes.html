Introduction to Kubernetes

Kubernetes is the system that runs and looks after containers for you, across many machines. You'll learn what problems it solves, what it gives you out of the box, and how it differs from Docker.

Quick recap: containers

A container packages an application together with everything it needs to run (libraries, runtime, settings). Unlike a virtual machine, it does not carry a whole operating system, so it starts in seconds and uses very little memory. Docker is the best-known tool for building and running containers.

Containers solved the "it works on my machine" problem, and they suit microservices (many small services instead of one big app). But once a company runs hundreds or thousands of them, new problems appear. That is where Kubernetes comes in. This lesson assumes you already know basic Docker and containers.

NoteKubernetes is a big topic, but the first step is the easy one: understanding why it exists. If you get the four problems below, you already have the foundation, and the rest builds on it. Job listings for DevOps roles almost always mention Kubernetes, so it is worth the effort.

What is Kubernetes?

Kubernetes (often written K8s, because there are 8 letters between the K and the s) is an open-source container orchestration platform. The one-line answer for an interview: Docker is a container platform; Kubernetes is a container orchestration platform. "Orchestration" means one system decides where containers run, keeps them healthy, and adjusts them as needs change.

It came out of Google, which had run containers at enormous scale with an internal, closed-source system called Borg. Kubernetes is the open-source, enterprise-grade platform built from those lessons. It is now backed by a large community under the Cloud Native Computing Foundation (CNCF), which also hosts tools like Prometheus.

Think of it like…An orchestra conductor. The musicians (containers) know how to play, but someone must decide who plays when, replace a musician who leaves, and add more players for a louder passage. Kubernetes is that conductor.

Problems with plain Docker

Containers are ephemeral: short-lived, they can die and be replaced at any time. Running them with Docker on a single server works well for learning. In production, four problems show up.

1. Single host

All containers share one machine. Say you run 100 containers and container 1 suddenly eats a lot of memory. The Linux kernel must free memory by killing some process, so container 100, which has nothing to do with container 1, may die or never start. If the machine dies, everything dies.

2. No auto-healing

If a container crashes or is killed, the app is unreachable until a person notices and restarts it. On a laptop that's fine; with 10,000 containers nobody can keep running docker ps to check, and customers shouldn't be your alarm system.

3. No auto-scaling

Imagine a streaming site where a hit movie is released and users jump from 10,000 to a million. Someone must start more copies by hand and set up a load balancer, because users only know one URL and can't be told "you go to this IP, you go to that one."

4. No enterprise features

Docker is deliberately minimal. A company app needs a load balancer, firewall-style controls (allow or block certain clients, protect against denial-of-service attacks), scaling, healing and an API gateway. Plain Docker offers none of these by default.

How Kubernetes solves them

  • Cluster, not a single host. Kubernetes joins many machines (called nodes) into one cluster, typically one or more control-plane ("master") nodes plus several worker nodes. If a faulty app is hurting its neighbours on one node, Kubernetes can place the affected Pod on a different node. (You can run a one-node cluster, but that's for learning, not production.)
  • Auto-scaling. Everything in Kubernetes is described in YAML files. To handle tomorrow's festival traffic you change replicas: 1 to replicas: 10 and apply it (manual scaling). Or you use the Horizontal Pod Autoscaler (HPA): "when CPU load passes 80%, add another copy," and it keeps adding as load grows from thousands to millions.
  • Self-healing. A ReplicaSet (the newer name for the old "replication controller") keeps the requested number of copies alive. When Kubernetes sees a container is failing it rolls out a replacement, often before the old one is fully gone, so users barely notice. (In Kubernetes you mostly deal with Pods, which wrap containers. More in Lesson 4.)
  • Load balancing and service discovery. Traffic is spread across the copies, and apps find each other by name instead of by changing IP addresses (see Lesson 6: Services).
  • Safe updates. New versions roll out gradually, and you can roll back if something breaks (see Lesson 5: Deployments).

Kubernetes also fills the "enterprise" gap, but be honest about it: it does not solve everything out of the box. By default it only gives basic load balancing (round robin, via Services and kube-proxy). Instead it is extensible: with custom resources and custom controllers, other projects plug in more. The best-known example is ingress controllers, where a load balancer like NGINX plugs in to give advanced routing. That openness, plus the CNCF community improving it every day, is why adoption keeps growing.

The idea behind all of it is desired state: you describe what you want, and Kubernetes keeps working until reality matches. Try it below.

Kubernetes vs Docker

This is not a fight: they work at different levels. Docker builds and runs one container on one machine. Kubernetes manages many containers across many machines. Kubernetes still needs a container runtime on every node to actually run containers (today usually containerd; Docker images work fine).

Interview angle"What is the difference between Docker and Kubernetes?" Short answer: container platform vs container orchestration platform. Then give the four problems: single host, no auto-healing, no auto-scaling, no enterprise features (load balancer, firewall rules, API gateway), and how Kubernetes answers each. Also be ready to say Docker alone isn't used for production.

Key takeaways

  • Kubernetes (K8s) is an open-source platform that orchestrates containers across a cluster of machines.
  • It fixes Docker's production gaps: single host, no auto-healing, no auto-scaling, no enterprise features.
  • You declare a desired state, and Kubernetes keeps reality matching it.
  • Key features: self-healing, scaling, load balancing, rolling updates, config and storage handling.
  • Docker runs containers; Kubernetes manages them at scale. They complement each other.
