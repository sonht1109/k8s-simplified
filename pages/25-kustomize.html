Kustomize

The same app usually runs in dev, staging and production with small differences: replica counts, image tags, names. Kustomize lets you keep one base YAML and describe only the differences, with no copying and no templates.

Deployments and their replicas and image fields are explained in Lesson 5. Kustomize and Helm (Lesson 27) solve a similar problem in different ways.

The problem

You have an nginx Deployment. Dev needs 3 replicas, staging 4, production 5. With plain kubectl apply you would make folders dev/, stage/, prod/, each with a nearly identical copy of the file. Then six months later a security fix means updating the image in every copy. With 50 microservices and 3 environments that is 150 files to edit by hand, and one will be forgotten.

Kustomize fixes this. It is built into kubectl (and also available as a standalone kustomize command) and is a template-free configuration tool: your YAML stays valid, ordinary Kubernetes YAML, and you layer changes on top.

Think of it like…Ansible for servers lets you say "install nginx on all VMs, but a different version on one". Kustomize does the same for manifests: one shared definition, plus small per-environment tweaks.

Bases and overlays

  • A base is the common, original set of manifests (Deployment, Service, ConfigMap...).
  • An overlay is a folder per environment that points at the base and says what to change.
myapp/
├── base/
│   ├── deployment.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    └── stage/
        └── kustomization.yaml

Step by step

1. The base. base/deployment.yaml is a normal Deployment (name nginx-deployment, 1 replica, image nginx:1.14.2). Next to it, a kustomization.yaml lists which files belong to the base:

# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- deployment.yaml

Add a Service, ConfigMap or Ingress later by listing it under resources.

2. An overlay. It points at the base and adds transformers, built-in instructions for common changes:

# overlays/dev/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base
namePrefix: dev-
images:
- name: nginx
  newTag: latest

The resources path can also be a Git URL, so a platform team can keep shared bases in one repository while app teams keep only overlays.

3. Preview, then apply.

kubectl kustomize overlays/dev          # print the final YAML, change nothing
kubectl create namespace dev
kubectl apply -k overlays/dev -n dev    # note: -k, not -f

The Deployment is now called dev-nginx-deployment and uses nginx:latest, and base/deployment.yaml was never touched. This also solves a common team problem: two developers sharing a namespace each use a different prefix and no longer overwrite each other's Deployments.

Common built-in transformers

FieldWhat it does
namePrefix / nameSuffixAdds text to every resource name
namespaceSets the namespace of all resources
imagesChanges image name or tag
replicasSets replica count by resource name
commonLabels / commonAnnotationsAdds labels or annotations to everything

The Kustomize documentation lists about a dozen. Check there before writing patches by hand.

Patches: change anything

What if no transformer fits, for example a field in a custom resource? Use patches. There are two styles; pick whichever you find more comfortable.

Style 1: YAML (strategic merge) patch

Write a small YAML file containing just enough of the resource to identify it, plus the field you change:

# overlays/dev/replicas.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 4
# overlays/dev/kustomization.yaml (add)
patches:
- path: replicas.yaml

Style 2: JSON patch

Give an operation and a path. Because it does not say which resource, you add a target:

# overlays/stage/replicas.yaml
- op: replace
  path: /spec/replicas
  value: 5
# overlays/stage/kustomization.yaml (add)
patches:
- path: replicas.yaml
  target:
    group: apps
    version: v1
    kind: Deployment
    name: nginx-deployment

Both do the same thing. YAML patches are easier to read; JSON patches are handy for precise edits such as an item inside a list of containers.

Generators

Kustomize can also create ConfigMaps and Secrets from literals or files with configMapGenerator and secretGenerator. It appends a hash to the name, so changing the content triggers a rolling restart of Pods that use it. They are useful but less commonly used than patches and transformers.

Kustomize vs Helm

  • Kustomize: no templates, plain YAML plus overlays. Simple, built into kubectl. Good for per-environment tweaks.
  • Helm: templates plus a values file, and also a package manager with releases and rollbacks. More powerful, more to learn. See Lesson 27.

Many teams even combine them. Pick Kustomize when you want the simpler approach.

Check yourself

Which command applies an overlay folder?
Kustomize directories are applied with -k. kubectl kustomize <dir> only prints the result.
A new nginx security fix needs one image tag change for all environments. With a shared base, where do you edit?
Overlays inherit from the base, so a shared change goes in one place. Overlays that set their own images tag keep theirs.
Why choose Kustomize over Helm for a simple setup?
Kustomize keeps manifests as normal YAML. Helm uses templates and adds package management.

Key takeaways

  • Kustomize customizes plain YAML without templates, and is built into kubectl.
  • Put shared manifests in a base and per-environment changes in overlays.
  • Each folder needs a kustomization.yaml; overlays reference the base under resources.
  • Use built-in transformers (namePrefix, images, replicas) or patches (YAML or JSON style).
  • Preview with kubectl kustomize, deploy with kubectl apply -k.
