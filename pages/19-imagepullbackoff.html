Troubleshooting: ImagePullBackOff

One of the first errors every Kubernetes beginner meets: the Pod never starts because its container image cannot be downloaded. You will learn what the name means, the three common causes, how to tell them apart with kubectl describe, and how to fix each.

Pods and their YAML are explained in Lesson 4. Secrets (used below for registry logins) are covered in Lesson 13.

What the name means

Before a Pod can run, the kubelet (the agent on the node) must pull the container image from a registry such as Docker Hub, Amazon ECR or Azure ACR. If the pull fails you see two statuses, one after the other:

  • ErrImagePull: the first failed attempt.
  • ImagePullBackOff: Kubernetes is now waiting before trying again. The wait grows each time (roughly 5s, 10s, 20s, 40s ... up to a cap of 5 minutes). This growing delay is the "back-off".

The wait exists because the failure may be temporary, like a network blip. Kubernetes keeps trying, but politely. It affects any Pod, whether created directly or by a Deployment, StatefulSet, DaemonSet or ReplicaSet.

Cause 1: wrong image name or tag

The most common cause is a typo, or an image or tag that does not exist (or was deleted). An image reference has the shape registry/repository:tag. With no registry, Docker Hub is assumed.

containers:
  - name: nginx
    image: nginy:1.14.2      # typo: there is no "nginy" repository

Same problem for myapp:1.1.1 when that tag was removed from the registry. For a registry other than Docker Hub you must include its address, for example 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:v1.

Fix: correct the image in the manifest and re-apply. A Deployment creates fresh Pods:

kubectl apply -f nginx-deploy.yaml
# or fix it directly:
kubectl set image deployment/nginx-deployment nginx=nginx:1.14.2

Cause 2: private image, no credentials

The image exists but the repository is private. Without a login, the registry refuses the pull ("pull access denied" or "authorization failed"). Kubernetes needs the credentials, stored in a Secret of type docker-registry and referenced from the Pod as an imagePullSecret.

  1. Create the Secret (the name regcred is your choice): 
    kubectl create secret docker-registry regcred \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=<your-username> \
  --docker-password=<your-password-or-token> \
  --docker-email=<your-email>
    Check it with kubectl get secrets. The type shows as kubernetes.io/dockerconfigjson.
  2. Reference it in the Pod spec, in the same namespace: 
    spec:
  imagePullSecrets:
    - name: regcred
  containers:
    - name: nginx
      image: myuser/nginx-image-demo:v1
  3. Apply and watch: kubectl apply -f nginx-deploy.yaml then kubectl get pods -w.
Watch outTwo classic slips even after adding the Secret: using the image name without your username prefix (nginx-image-demo instead of myuser/nginx-image-demo), and a Secret in a different namespace from the Pod. Also a typo in the username or password makes the Secret useless.

Other registries: the same command works. Only the values change. For Amazon ECR:

kubectl create secret docker-registry ecr-cred \
  --docker-server=<ACCOUNT_ID>.dkr.ecr.<REGION>.amazonaws.com \
  --docker-username=AWS \
  --docker-password="$(aws ecr get-login-password --region <REGION>)"

For Azure ACR or others, look up the registry's docs for the server name and credentials. ECR tokens expire after 12 hours, so teams usually refresh them automatically, or on EKS give the nodes an IAM role that can read ECR.

Cause 3: network or registry problems

The name is right and the credentials are fine, but the node cannot reach the registry: no internet or NAT route from a private subnet, a firewall or proxy, DNS failure, or the registry itself is down or rate-limiting you. These often clear up on their own, which is why Kubernetes keeps retrying. If not, test from the node itself (for example curl the registry or try docker pull/crictl pull) and fix routing or DNS.

The debug flow

  1. kubectl get pods: confirm the status is ErrImagePull or ImagePullBackOff.
  2. kubectl describe pod <pod-name>: scroll to the Events section at the bottom. This is where the real reason is written.
  3. Read the message and match it to a cause (table and demo below).
  4. Fix, re-apply, and watch with kubectl get pods -w (the -w flag keeps updating the list).
kubectl describe pod nginx-deployment-7c8f5d-abcde
...
Events:
  Warning  Failed  Failed to pull image "nginy:1.14.2": ... repository does not exist or may require authorization
  Warning  Failed  Error: ErrImagePull
  Normal   BackOff Back-off pulling image "nginy:1.14.2"
  Warning  Failed  Error: ImagePullBackOff

You can also list cluster events directly: kubectl get events --sort-by=.lastTimestamp.

Check yourself

What does the "BackOff" in ImagePullBackOff mean?
After each failure the delay grows (up to about 5 minutes) before the next attempt.
The event says "pull access denied" for an image that definitely exists. What is the likely fix?
A private repository needs credentials. Store them in a Secret and reference it from the Pod.
Where do you find the actual reason for the failed pull?
The container never started, so there are no logs. The kubelet's pull errors appear in Events.

Key takeaways

  • ErrImagePull is the first failure; ImagePullBackOff is the waiting state with growing retry delays.
  • Three causes: wrong image name or tag, private registry without credentials, network or registry problems.
  • Always start with kubectl describe pod and read the Events at the bottom.
  • Private images need a docker-registry Secret and imagePullSecrets in the same namespace.
  • The same approach works for ECR, ACR and others, only the server and credentials differ.
