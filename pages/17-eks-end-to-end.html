Project: End-to-End App on EKS

Build something you can show on a resume: create an Amazon EKS cluster, deploy the 2048 game, and expose it to the internet through an Application Load Balancer that Kubernetes creates for you. The focus is on the build steps and why each one is needed.

This project uses ideas taught elsewhere: Deployments, Services, Ingress and ingress controllers, and Helm. Here we only wire them together on AWS.

What is EKS?

EKS (Elastic Kubernetes Service) is AWS's managed Kubernetes. If you build a cluster yourself (kubeadm, kOps), you own everything: a broken etcd, an expired certificate, a slow API server. With EKS:

  • AWS runs the control plane (API server, etcd, scheduler, controllers) across several Availability Zones, with an SLA. You never see those machines.
  • You choose the worker nodes (the data plane): your own EC2 instances (in node groups with autoscaling), or Fargate, AWS's serverless compute for containers, where you do not manage servers at all.

The architecture of control plane and nodes is in Lesson 2. Note that "managed" does not mean "self-upgrading". See Lesson 16.

The plan

A Pod is only reachable inside the cluster. To reach it from the internet, you need a path. In a VPC, apps live in private subnets and the load balancer lives in public subnets.

Step 0: Install the tools

On your laptop you need kubectl (talks to the cluster), eksctl (creates and manages EKS clusters), the aws CLI (configured with aws configure) and helm. Use an IAM user with enough permissions in a practice account, and delete everything when done to avoid charges.

Step 1: Create the cluster

eksctl create cluster --name demo-cluster --region us-east-1 --fargate

This takes 10-20 minutes. Behind the scenes eksctl creates a VPC with public and private subnets, the IAM roles, the managed control plane and a default Fargate profile. Doing the same by clicking in the console needs many more decisions, which is why teams prefer eksctl (or Terraform).

Then point kubectl at the new cluster:

aws eks update-kubeconfig --name demo-cluster --region us-east-1
kubectl get nodes
HandyThe EKS console has a Resources tab where you can browse Pods, DaemonSets and ServiceAccounts without typing kubectl.

Step 2: Create a Fargate profile for your namespace

On Fargate, a Pod only runs if its namespace matches a Fargate profile. The default profile covers only default and kube-system. Our app will live in game-2048, so add a profile:

eksctl create fargateprofile \
  --cluster demo-cluster --region us-east-1 \
  --name alb-sample-app --namespace game-2048
Watch outIf you forget this, your Pods sit in Pending forever. With EC2 node groups you do not need Fargate profiles.

Step 3: Deploy the app, Service and Ingress

One manifest holds four objects: a Namespace, a Deployment (5 replicas of the 2048 game image), a Service, and an Ingress. The key parts:

apiVersion: v1
kind: Service
metadata:
  namespace: game-2048
  name: service-2048
spec:
  type: NodePort
  selector:
    app.kubernetes.io/name: app-2048   # must match the Pod labels
  ports:
    - port: 80
      targetPort: 80
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  namespace: game-2048
  name: ingress-2048
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: service-2048
                port:
                  number: 80

Apply it and look around:

kubectl apply -f 2048_full.yaml
kubectl get pods -n game-2048
kubectl get svc -n game-2048
kubectl get ingress -n game-2048

The Pods run, but the Ingress has no ADDRESS. An Ingress is only a set of rules. Nothing in the cluster is reading it yet. Selectors and Services are explained in Lesson 6; the Ingress idea in Lesson 9.

  • scheme: internet-facing puts the ALB in public subnets with a public address.
  • target-type: ip sends traffic straight to Pod IPs. It is required on Fargate.
  • ingressClassName: alb tells the AWS controller that this Ingress is its job.

Step 4: Install the AWS Load Balancer Controller

The controller is itself a Pod. It must call AWS APIs to create load balancers, so it needs AWS permissions. EKS does this with IAM roles for service accounts (IRSA): a Kubernetes ServiceAccount is linked to an IAM role through an OIDC identity provider.

  1. Associate the IAM OIDC provider with the cluster: 
    eksctl utils associate-iam-oidc-provider \
  --cluster demo-cluster --region us-east-1 --approve
  2. Create the IAM policy from the JSON published in the controller's documentation: 
    curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json
aws iam create-policy \
  --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json
  3. Create a ServiceAccount bound to a role that carries the policy (replace <ACCOUNT_ID>): 
    eksctl create iamserviceaccount \
  --cluster demo-cluster --region us-east-1 \
  --namespace kube-system --name aws-load-balancer-controller \
  --role-name AmazonEKSLoadBalancerControllerRole \
  --attach-policy-arn arn:aws:iam::<ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve
  4. Install the controller with Helm, reusing that ServiceAccount (replace the VPC id; find it on the cluster's Networking tab): 
    helm repo add eks https://aws.github.io/eks-charts
helm repo update eks
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=demo-cluster \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=us-east-1 \
  --set vpcId=<VPC_ID>
  5. Wait until it is ready (2 of 2 replicas, one per Availability Zone): 
    kubectl get deployment -n kube-system aws-load-balancer-controller

Step 5: Watch the magic happen

As soon as the controller runs, it sees the Ingress and creates an ALB with listeners, target groups and security groups. In a couple of minutes:

kubectl get ingress -n game-2048     # ADDRESS now shows the ALB DNS name

Open that address in a browser (plain http://) once the load balancer shows Active in the EC2 console. You should see the 2048 game. Notice the pattern that real teams use: a DevOps engineer sets up the controller once, and every microservice team only writes Deployment, Service and Ingress YAML.

Troubleshooting you may meet

  • Controller Pods stuck at 0/2: run kubectl describe on the Deployment or ReplicaSet. A message like "error looking up service account" means the ServiceAccount was not created (often a leftover CloudFormation stack from a previous try; delete the stack and recreate).
  • "policy already exists": an earlier run left it behind. Reuse or delete it.
  • Pods Pending: missing Fargate profile for the namespace.
  • ALB created but the page does not load: wait until its state is Active, and check you used http://.
Clean upThe cluster, ALB and Fargate Pods all cost money. Delete the Ingress first (so the controller removes the ALB), then run eksctl delete cluster --name demo-cluster --region us-east-1.

Check yourself

You applied an Ingress with ingressClassName: alb but ADDRESS stays empty. Most likely cause?
An Ingress is just rules. A controller must watch it and create the load balancer.
Why does the controller need an OIDC provider and an IAM-linked ServiceAccount?
IRSA lets a Kubernetes ServiceAccount assume an IAM role, giving the controller Pod permission to call AWS APIs.
What does "EKS is a managed control plane" mean?
You still choose and look after the data plane (or use Fargate), and you still trigger upgrades.

Key takeaways

  • EKS = AWS-managed control plane; workers are EC2 node groups or serverless Fargate.
  • eksctl create cluster builds the VPC, subnets, roles and cluster in one command.
  • On Fargate, every namespace needs a Fargate profile or Pods stay Pending.
  • An Ingress needs an ingress controller; on AWS that is the Load Balancer Controller, which creates an ALB.
  • The controller gets AWS permissions via an OIDC provider, an IAM policy and an IAM-linked ServiceAccount.
  • Set up the controller once; each app team then ships only Deployment, Service and Ingress.
