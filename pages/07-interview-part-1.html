The questions

1. What is the difference between Docker and Kubernetes?

Docker is a container platform; Kubernetes is a container orchestration platform. Docker builds and runs containers on a single machine. Kubernetes runs containers across a cluster of machines and manages them for you.

  • Self-healing: containers are short-lived. Kubernetes replaces failed ones automatically.
  • Scaling: add or remove replicas by hand or automatically.
  • No single-host limit: if a node dies, Pods move to other nodes. With plain Docker, if the host dies, the app is down.
  • Enterprise features: load balancing, and extensibility through custom resources and controllers (for example ingress controllers).

Full story: Lesson 1: Intro to Kubernetes.

2. What are the main components of Kubernetes architecture?

Split it into the control plane (the brain) and the worker nodes (where apps run).

Control plane

  • API server: the front door; every request goes through it.
  • etcd: the database where all cluster state is stored.
  • Scheduler: decides which node runs each new Pod.
  • Controller manager: runs the built-in controllers (ReplicaSet, Node, and so on).
  • Cloud controller manager: talks to the cloud provider, for example to create a load balancer.

Worker node

  • kubelet: manages Pods on the node.
  • kube-proxy: programs network rules for Services.
  • Container runtime: actually runs containers (containerd, CRI-O).
Follow-up you may get"If Kubernetes does not ship Docker by default, does it not support Docker?" Kubernetes supports any runtime that implements the Container Runtime Interface (CRI). Container images built with Docker run fine on containerd or CRI-O. You just have to install a runtime on every node, because none is built in.

Details: Lesson 2: Architecture.

3. What is the difference between Docker Swarm and Kubernetes?

Both orchestrate containers. The difference is scale and ecosystem.

  • Docker Swarm is very easy to install and use, but it is best for small or simple setups and has limited networking and extension options.
  • Kubernetes suits mid-size and large organisations. It supports advanced networking (Calico, Flannel and others), has a very active community (CNCF), and can be extended with custom resource definitions and controllers when something is missing.
  • Market reality: almost every DevOps job description asks for Kubernetes.

See Lesson 12: CRDs & Custom Controllers for the extension model.

4. What is the difference between a Docker container and a Kubernetes Pod?

A container is one running process packaged with its dependencies. A Pod is the smallest deployable unit in Kubernetes: a wrapper that runs one or more containers, described in a YAML manifest.

  • Containers in the same Pod share one network namespace (they talk over localhost) and can share storage volumes.
  • The Pod spec also carries things a bare container lacks: labels, resource requests, probes, restart policy.

See Lesson 4: Pods, and Lesson 5 for why you rarely create bare Pods in production.

5. What is a namespace in Kubernetes?

A namespace is a logical partition inside one cluster. Companies rarely build one cluster per team, so many teams share one cluster, and each team works in its own namespace.

  • Names only need to be unique within a namespace, so two teams can both have a Deployment called web.
  • You can attach access rules (RBAC), resource quotas and network policies per namespace, so one team cannot touch another team's resources.
  • It is logical isolation only: the Pods may still run on the same physical nodes.
kubectl create namespace team-a
kubectl get pods -n team-a
kubectl get pods --all-namespaces
6. What is the role of kube-proxy?

kube-proxy runs on every node and implements Services at the network level. It watches the API server for Services and their endpoints and writes network rules on the node, by default with iptables (IPVS is another mode).

Example: you create a NodePort Service. kube-proxy adds rules so that traffic arriving at <node-ip>:<nodePort> is forwarded to one of the Pods behind the Service. The routing is done by the Linux kernel using those rules.

See Lesson 6: Services.

7. What are the different types of Services? How do they differ?

Three main types, each adding reach:

  • ClusterIP (default): a virtual IP reachable only inside the cluster.
  • NodePort: also opens a port (30000-32767) on every node, so anyone who can reach the node IPs can use the app.
  • LoadBalancer: also asks the cloud provider (via the cloud controller manager) for a public load balancer, so anyone on the internet can reach it.

There are also ExternalName and headless Services. Hands-on: Lesson 8: Services Deep Dive.

8. What is the difference between NodePort and LoadBalancer?

NodePort exposes the app on every node's IP and a high port. It works for people who can reach your nodes (your office network or VPC), but users must know a node IP and an odd port, and you must open that port range on the firewall.

LoadBalancer builds on NodePort and adds an external load balancer with its own public address, so users outside your organisation can reach the app. It needs a cloud provider (or a tool such as MetalLB on bare metal). On a laptop cluster the external IP stays <pending>.

One more reason to know the answer: LoadBalancer costs money per Service, which is why Ingress exists.

9. What is the role of the kubelet?

The kubelet is the agent on each worker node that manages the Pods on that node. The scheduler assigns a Pod to a node; the kubelet makes it real.

  • It tells the container runtime to start the containers.
  • It runs health checks (probes) and restarts containers that fail.
  • It continuously reports Pod and node status to the API server. If a Pod is missing, controllers (like the ReplicaSet controller) see that and create a replacement, as explained in Lesson 5.
10. What are your day-to-day activities on Kubernetes?

This is often the first question, so a calm, simple answer sets the tone. Cover these areas honestly, using what you really do or have practised:

  • Operate clusters: keep them healthy, set up monitoring and alerts.
  • Deploy and release applications: manifests, Deployments, rollouts and rollbacks.
  • Troubleshoot: help developers when Pods will not start or Services do not route traffic (kubectl describe, logs, events).
  • Maintain: upgrade Kubernetes versions on nodes, patch packages, fix security vulnerabilities (see Lesson 3).
  • Support: answer tickets and teach teams how Kubernetes works.
TipA good answer has three parts: a one-sentence definition, one or two key points, and a real example. For instance: "kube-proxy configures iptables rules on each node. For example, when I create a NodePort Service, it routes node-IP:port to the Pods."

Check yourself

Which component decides which node a new Pod runs on?
The scheduler picks the node. The kubelet on that node then starts the Pod.
A teammate says "Kubernetes dropped Docker, so it cannot run Docker images." What is the right response?
Images follow an open standard. Any CRI runtime can run them.
Which statement about namespaces is correct?
Namespaces are logical isolation within a single cluster, combined with RBAC and quotas.

Key takeaways

  • Docker runs containers on one host; Kubernetes orchestrates them across a cluster with self-healing, scaling and load balancing.
  • Control plane: API server, etcd, scheduler, controller manager, cloud controller manager. Worker: kubelet, kube-proxy, container runtime.
  • A Pod wraps one or more containers that share network and storage.
  • Namespaces give logical isolation; ClusterIP, NodePort and LoadBalancer give increasing reach.
  • Give short, structured answers: definition, key points, example.
