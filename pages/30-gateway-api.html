Gateway API

Gateway API is the modern way to bring outside traffic into a cluster. It fixes the two big problems of Ingress: very limited features and no clear split between platform and app teams. You'll learn its three resources and try weighted routing.

This lesson assumes you know what Ingress and ingress controllers are, and what a Service is. Gateway API resources are CRDs, which is why they can be installed and updated separately from Kubernetes.

The story so far: north-south traffic

Traffic inside the cluster (east-west, service to service) is easy because Kubernetes has its own network. Traffic from the outside world into the cluster (north-south) is harder. Kubernetes does not have a built-in load balancer.

Its answer was Ingress. Load-balancer makers (NGINX, HAProxy, cloud providers) write an ingress controller. The cluster admin installs it once. App teams then create Ingress resources and the controller builds the load balancer. It worked, but years of use revealed two drawbacks.

Drawback 1: Ingress can say very little

An Ingress can express only: "which Service" and "on which host or path". Real production needs more: rate limiting, a web application firewall, redirects, URL rewrites, canary (weighted) traffic, and so on. None of these exist in the Ingress spec.

Controllers worked around it with annotations. That created new pain:

  • Huge numbers of annotations (30 to 40 for one controller).
  • Some are JSON strings inside YAML, such as weighted routing for AWS ALB. Hard to read and easy to get wrong.
  • Annotations differ between NGINX, ALB and others, so switching controllers means relearning and rewriting.

Drawback 2: no separation of roles

In many companies the platform team owns the controller and which class to use, while app teams own routing for their service. With Ingress, both edit the same object, so an app developer can accidentally change what the platform team set up.

The community asked to split Ingress into parts. Changing Ingress itself would break everyone, so Kubernetes created something new.

Gateway API: three resources, three jobs

Gateway API solves the same problem as Ingress (north-south traffic), but split into three resources:

ResourceWhat it saysWho owns it
GatewayClassWhich controller implementation to use (like an IngressClass)Platform / cluster admin
GatewayThe entry point: which class, and which ports and protocols to listen onPlatform or app team (via RBAC)
HTTPRouteRouting rules: hosts, paths, backend Services, weights, filtersApp / DevOps team
  • Problem 1 solved: HTTPRoute has real fields for weights, redirects, header matches and rewrites. No more giant annotations.
  • Problem 2 solved: three separate resources means you can give each team RBAC permission on only the ones it owns (see Lesson 11).
  • It's also portable: the same resources work across controllers (Envoy Gateway, NGINX Gateway Fabric, Traefik, cloud implementations).
NoteRate limiting, WAF and similar features are still provided by the controller, often through extra policy resources it defines. Gateway API gives a standard place and shape for the common ones (redirects, rewrites, weights, header rules) instead of annotation strings.

Hands-on: from zero to a routed app

This demo uses a local cluster (see kind) and Envoy Gateway, a beginner-friendly controller.

Step 1: platform engineer installs the controller

The Helm chart installs the Gateway API CRDs and the controller in one go (see Lesson 27). Check the Envoy Gateway docs for the current version number.

kind create cluster --name gw-demo

helm install eg oci://docker.io/envoyproxy/gateway-helm \
  --version <version> -n envoy-gateway-system --create-namespace

kubectl get pods -n envoy-gateway-system
kubectl get crds | grep gateway

You should see gatewayclasses, gateways and httproutes CRDs. The controller now waits for Gateway and HTTPRoute objects, just as an ingress controller waits for Ingress objects.

Step 2: deploy an app with a ClusterIP Service

Any app will do. The demo app is a small "echo" server that replies with request details, exposed on port 3000.

kubectl create deployment backend --image=<your-echo-image>
kubectl expose deployment backend --port=3000

Step 3: GatewayClass (platform)

apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller

This says "anything using class eg is handled by Envoy Gateway". Many installs create it for you.

Step 4: Gateway (the entry point)

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: eg
spec:
  gatewayClassName: eg
  listeners:
  - name: http
    protocol: HTTP
    port: 80

gatewayClassName tells the Gateway which controller owns it (like ingressClassName). The listener says: listen on HTTP port 80. The controller creates a proxy Pod and a Service for it.

Step 5: HTTPRoute (the routing rules)

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: backend
spec:
  parentRefs:
  - name: eg
  hostnames:
  - "www.example.com"
  rules:
  - backendRefs:
    - name: backend
      port: 3000

parentRefs attaches the route to the Gateway. Requests with host www.example.com go to the backend Service on port 3000.

Step 6: test it

A local cluster can't create a cloud load balancer, so tunnel to the proxy's Service with port-forward. Find its name in the controller namespace first.

kubectl get svc -n envoy-gateway-system
kubectl port-forward -n envoy-gateway-system svc/<envoy-proxy-service> 9090:80

# in a second terminal
curl --verbose --header "Host: www.example.com" http://localhost:9090/

The reply comes from your backend Pod. The Host header matters: the route only matches that hostname.

Two features that used to need annotations

URL rewrite

Users call /get, but the app now serves /replace. Rewrite it in the route and nobody notices:

  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /get
    filters:
    - type: URLRewrite
      urlRewrite:
        path:
          type: ReplacePrefixMatch
          replacePrefixMatch: /replace
    backendRefs:
    - name: backend
      port: 3000

Weighted routing (canary)

With Ingress this was a JSON annotation. Now it is one field per backend:

  rules:
  - backendRefs:
    - name: app-v1
      port: 3000
      weight: 8
    - name: app-v2
      port: 3000
      weight: 2

Weights are relative, so 8 and 2 mean about 80% and 20%. Deployment strategies are explained in Lesson 18.

Try it: weighted routing

Set the weights of app-v1 and app-v2, then send 100 requests through the Gateway.

Interview angle"Why Gateway API over Ingress?" Richer routing built into the spec (no annotation sprawl), portable across controllers, and role-oriented design: GatewayClass for platform admins, Gateway and HTTPRoute for app teams.

Check yourself

Which resource does an application team normally write to define paths, hosts and backends?
HTTPRoute holds the routing rules. GatewayClass is chosen by the platform team.
What was a main complaint about Ingress that Gateway API fixes?
Ingress spec is small, so features moved into annotations, and one object mixed platform and app concerns.
How does an HTTPRoute connect to a Gateway?
parentRefs names the Gateway the route attaches to.

Key takeaways

  • Gateway API solves the same north-south traffic problem as Ingress, with fewer limits.
  • Three resources: GatewayClass (which controller), Gateway (entry point), HTTPRoute (rules).
  • Real fields replace annotation strings: weights, rewrites, redirects, header matching.
  • Role separation: platform owns the class, app teams own routes, enforced with RBAC.
  • Install a controller first; locally, use port-forward to reach the proxy.
  • Resources are CRDs, so they evolve independently of Kubernetes releases.
