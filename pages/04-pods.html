Pods: Deploy Your First App

The Pod is the smallest thing you can run in Kubernetes. You'll learn what it is, how to describe one in YAML, and the essential kubectl commands to create it, look at it, debug it and delete it.

Pods are scheduled onto nodes by the control plane. If you need the background, see Lesson 2: Architecture.

What is a Pod?

With Docker you run a container. In Kubernetes you cannot deploy a bare container: the lowest level of deployment is a Pod, a thin wrapper around one or more containers. You still build and use the same container images; you just deploy them as a Pod.

Think of a Pod as a definition of how to run a container. With Docker you pass everything on the command line:

docker run -d --name nginx -p 80:80 nginx

(-d runs it in the background, --name names it, -p maps a port, and you might also add -v for volumes or a network option.) In Kubernetes you write that same information in a YAML file instead. A Pod is, for a single container, almost the same thing as a Docker container; the difference is that the specification lives in a file rather than a long command.

Why the extra work? Kubernetes is an enterprise platform built on declarative files and standardisation. A developer or DevOps engineer can open the Pod file in a Git repository and immediately see the image, the port the app listens on, the volumes and so on, even with thousands of containers in production.

Why the extra layer? A Pod gives its containers a shared home:

  • One IP address for the whole Pod, so containers inside can talk to each other on localhost.
  • Shared storage (volumes) and shared network settings.
  • One lifecycle: they are scheduled, started and stopped together on the same node.
Think of it like…A Pod is a small apartment. Usually one person (container) lives there. Sometimes a helper lives there too, and they share the address, the kitchen, and the Wi-Fi.

In most cases, a Pod has exactly one container. Multiple containers are for tightly coupled helpers: sidecar containers (such as a log shipper or proxy running next to your app) and init containers (which run first to prepare things). For example, if your app needs to read files or call another container, putting both in one Pod lets them share networking and storage: container A can reach container B at localhost:3000, and they can share files. Multi-container Pods are a rare, advanced case; sidecars come back with service meshes later.

Kubernetes gives the Pod an IP address (via kube-proxy, see Lesson 2), not each container. You reach the app inside through that Pod IP.

Watch outA bare Pod does not get auto-healing or auto-scaling. If you delete it, or its node fails, nobody recreates it. In real production you rarely deploy bare Pods: you wrap them in a Deployment (or StatefulSet or DaemonSet). A Deployment is almost the same YAML with kind: Deployment and a Pod template, which is the next lesson. You still need Pods first, since a Deployment is just a wrapper around them.

Setting up

kubectl is the command line for Kubernetes, like the Docker CLI is for Docker. kubectl get nodes lists the machines, kubectl get pods lists Pods, kubectl get deployments lists Deployments, and so on. Install it from the official "install tools" page for your operating system (it's a copy-paste of a few commands), then check it:

kubectl version --client

You also need a cluster. Creating a real one on a cloud costs money (see Lesson 3), so for learning use a local cluster such as minikube, k3s, MicroK8s or kind. Minikube is the easiest start. (Kind, covered in Lesson 26, runs Kubernetes nodes as Docker containers and lets you create many clusters on one laptop, so it is a good next step.) These are not full production setups, but they are perfect for learning.

minikube start
kubectl get nodes

Minikube creates a virtual machine (or uses a Docker container) and runs a single-node cluster in it. That one node plays both control plane and worker, so kubectl get nodes shows one node named minikube with status Ready. You can choose how it runs, for example minikube start --driver=docker or another driver such as VirtualBox, depending on your system.

Your first Pod, the quick way

This one-liner is the Kubernetes version of the docker run above:

kubectl run nginx --image=nginx --port=80
kubectl get pods

The first command creates a Pod named nginx running the nginx image from Docker Hub. Right after, you may see ContainerCreating (the image is downloading), then Running.

This is handy for quick tests, but real teams describe objects in files, so their setup can be reviewed, versioned and repeated. Next we'll do it the file way.

Describing a Pod in YAML

Every Kubernetes object is written in YAML with four top-level fields:

apiVersion: v1          # which version of the API this object uses
kind: Pod               # what type of object
metadata:               # identity: name, labels, namespace
  name: nginx-pod
  labels:
    app: nginx
spec:                   # the desired state
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
  • apiVersion and kind say what you are creating. Pods are in the core API group, so just v1. (Deployments use apps/v1.)
  • metadata holds the name and optional labels (below).
  • spec is where you describe what you want. For a Pod, that's the list of containers: a name, an image, and the ports they listen on.

Compare with the Docker command earlier: image is the image, containerPort is the port the app listens on, and name is the name. Everything in Kubernetes (Pods, Deployments, Services) is written in YAML, so learn to read it well. But nobody memorises it: senior and junior engineers alike copy an example from the official Kubernetes docs and change the values (image, ports, names). The structure stays the same.

TipBookmark the official kubectl cheat sheet; even experienced engineers use it to look up commands. Don't memorise YAML. Generate a starting file with kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yaml, or use kubectl explain pod.spec to see every field.

Create and inspect it

kubectl create -f pod.yaml          # create from the file (apply -f also works)
kubectl apply -f pod.yaml           # create or update from the file
kubectl get pods                    # list Pods: name, ready, status, restarts, age
kubectl get pods -o wide            # adds the Pod IP and the node it runs on
kubectl describe pod nginx-pod      # full details + Events at the bottom
kubectl logs nginx-pod              # what the container printed
kubectl exec -it nginx-pod -- sh    # open a shell inside it
kubectl delete pod nginx-pod        # remove it
CommandWhen to use it
getQuick status check
describeSomething's wrong: read the Events section (image not found, can't schedule, and so on)
logsYour app crashed or misbehaves. Add -c name for a multi-container Pod
execLook around inside: check files, test connections

The kubectl get pods output is the equivalent of docker ps. With get pods -o wide you'll notice the Pod has an IP such as 10.244.0.5. That address works only inside the cluster. To test it, log into a cluster node (with minikube, minikube ssh; on a real cluster, SSH to a node) and run curl 10.244.0.5. With nginx you get the welcome page. The address also changes if the Pod is replaced. Giving Pods stable addresses is the job of Services. For a quick peek from your laptop, kubectl port-forward pod/nginx-pod 8080:80 works (see Lesson 24).

Labels

Labels are key-value tags you put on objects, like app: nginx or env: prod. They do nothing by themselves, but other objects use them to select Pods: Deployments and Services find "their" Pods by label.

kubectl get pods --show-labels
kubectl get pods -l app=nginx          # filter by label
kubectl label pod nginx-pod env=dev    # add a label

Multi-container Pods (briefly)

List more than one entry under containers:

spec:
  containers:
    - name: app
      image: my-app:1.0
    - name: log-shipper
      image: fluent/fluent-bit:3.0

Both share the Pod's IP and can share volumes. READY will show 2/2 when both are up.

Interview angle"How do you debug a Pod?" Your two go-to commands: kubectl describe pod NAME (status, errors and events) and kubectl logs NAME (what the app printed).
Interview angle"Why does Kubernetes use Pods instead of running containers directly?" Because some containers must share networking and storage and be scheduled together. The Pod is the unit of scheduling. Mention sidecars, and that bare Pods don't self-heal.

Key takeaways

  • A Pod wraps one or more containers that share an IP, storage and lifecycle. One container per Pod is the norm.
  • Manifests have apiVersion, kind, metadata and spec.
  • Core commands: apply -f, get, describe, logs, exec, delete.
  • describe and its Events are your first stop when a Pod misbehaves.
  • Labels tag objects so other objects can find them.
  • Bare Pods don't heal themselves, so next we use Deployments.
