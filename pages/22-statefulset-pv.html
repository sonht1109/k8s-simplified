StatefulSets & Persistent Volumes

Databases and other apps that must remember things need storage that outlives a Pod. You will learn how Kubernetes provides it (PV, PVC, StorageClass), how a StatefulSet differs from a Deployment, and how to fix the classic "works on EKS, Pending everywhere else" bug.

Stateless apps are handled by Deployments, covered in Lesson 5. Pods themselves are in Lesson 4.

A real-world problem

A developer files a ticket: "My StatefulSet works on our AWS EKS cluster, but on AKS, GKE and minikube the Pods never start." You get the same YAML. Where do you look? To answer that you need the storage building blocks first.

Why storage needs special handling

A container's own filesystem disappears when the container is replaced. That is fine for a web server and a disaster for a database. Kubernetes separates asking for storage from providing storage using three objects:

PersistentVolume (PV)

A piece of real storage in the cluster: an AWS EBS disk, an Azure disk, a folder on a node. It exists independently of any Pod.

PersistentVolumeClaim (PVC)

A Pod's request: "I need 1 GiB, read/write by one node". Kubernetes binds the claim to a matching PV.

StorageClass

A recipe for creating PVs on demand: which kind of storage and which provisioner. Names like standard or gp3 are classes.

Provisioner / CSI driver

The plugin that talks to the storage system and creates the PV when a PVC asks for it.

Think of it like…A PVC is an order form ("one 1 GiB disk, fast type, please"). The StorageClass is the catalogue entry that says which supplier fulfils it. The provisioner is the supplier, and the PV is the disk that arrives.

StatefulSet vs Deployment

A StatefulSet runs Pods that need a stable identity. Compared to a Deployment:

  • Stable names: Pods are called web-0, web-1, web-2, not random hash names. Replace web-1 and the new one is again web-1.
  • Own storage per Pod: a volumeClaimTemplates section creates a separate PVC for each Pod (data-web-0, data-web-1...). Each Pod keeps its disk when it restarts.
  • Ordered start: web-1 is only created after web-0 is Running and ready, then web-2 after web-1. Think of a database: you want the primary up before the replicas that copy from it.

Stable DNS names for each Pod come from a headless Service, see Lesson 29.

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: web
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: ebs        # the cause of our bug
      resources:
        requests:
          storage: 1Gi

Debugging the ticket

Apply the file on minikube and look:

kubectl apply -f statefulset.yaml
kubectl get statefulset      # READY 0/3
kubectl get pods             # only web-0, and it is Pending

Only one Pod appears because of the ordered start. It is not a separate bug. Now ask Kubernetes why:

kubectl describe pod web-0
# Warning  FailedScheduling  ...  pod has unbound immediate PersistentVolumeClaims

"Unbound" means the Pod's claim never got a volume. Follow the chain from the diagram:

kubectl get pvc              # data-web-0   Pending
kubectl describe pvc data-web-0   # storageclass "ebs" not found
kubectl get storageclass     # minikube has only: standard

Root cause: the YAML asks for a StorageClass named ebs. EKS had a class by that name backed by AWS EBS, but minikube only has standard. No class, no provisioner, no volume.

The fix

  1. Change storageClassName to a class that exists (standard on minikube). Better still, leave the field out and the cluster's default class is used, which makes the same YAML portable.
  2. Delete the old StatefulSet: kubectl delete -f statefulset.yaml.
  3. Delete the leftover PVCs too: kubectl delete pvc -l app=web (or by name). Deleting a StatefulSet does not delete its PVCs or volumes, on purpose, to protect your data. The old Pending claim would otherwise stay stuck with the wrong class.
  4. Apply again and watch kubectl get pods -w. web-0 goes Running, then web-1 appears, then web-2.
Watch outBecause PVCs survive deletion, think before removing them in production. They hold the data. The "delete PVC" step above is safe only here because the claims never bound to anything.

External storage and CSI drivers

Clouds ship drivers for their own disks. What if you want storage from a vendor the cluster does not know, such as NetApp? The vendor supplies a CSI driver (Container Storage Interface), usually installed with a Helm chart or operator. Once installed, you create a StorageClass that points to it, and PVCs using that class get volumes from the vendor. Everything else in the chain stays the same.

Storage troubleshooting checklist

  • Pod Pending with "unbound PVC" → kubectl describe pvc.
  • Does the named class exist? kubectl get storageclass (look for (default)).
  • Is the provisioner or CSI driver running? kubectl get pods -A | grep -i provisioner.
  • Old PVCs left over from a previous attempt? Check kubectl get pvc,pv.

You delete a StatefulSet. What happens to its PersistentVolumeClaims?
Kubernetes keeps PVCs (and the data) so deleting a StatefulSet does not destroy your database.

Key takeaways

  • A PVC requests storage; a StorageClass and provisioner create the PV that satisfies it.
  • A StatefulSet gives Pods stable names, one PVC each, and ordered startup.
  • "Works on EKS, not elsewhere" often means a missing StorageClass. Omit the name to use the default.
  • Deleting a StatefulSet leaves PVCs behind; clean them up deliberately.
  • Third-party storage needs a CSI driver installed first.
