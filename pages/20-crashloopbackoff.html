Troubleshooting: CrashLoopBackOff

Your Pod starts, crashes, restarts, crashes again. Kubernetes shows CrashLoopBackOff. It is a symptom, not a single bug, so you will learn the loop itself, the most common causes (bad command, failing probe, out of memory, app errors) and a debug flow built on logs --previous and describe.

Pods are covered in Lesson 4; the Deployment that keeps restarting them in Lesson 5. A different start-up failure, a bad image, is in Lesson 19: ImagePullBackOff.

What is happening

When you apply a Deployment, the scheduler picks a node and the node's kubelet runs the Pod. Its normal life: ContainerCreating, then Running. But the application inside the container can exit or be killed at any moment: right away, after 5 seconds or after a day.

By default a Pod's restartPolicy is Always, so the kubelet restarts the container each time. If it keeps crashing, Kubernetes inserts a growing pause between restarts: about 10s, 20s, 40s ... capped at 5 minutes. A crash repeating in a loop with a back-off delay is CrashLoopBackOff.

Common causes

1. Wrong command or arguments

The container's start command is wrong, for example python3 app1.py when the file is app.py. It fails instantly every time.

2. Failing liveness probe

The kubelet checks health; if the check keeps failing it kills and restarts the container.

3. Out of memory (OOMKilled)

The container uses more memory than its limit, so the system kills it.

4. App or config errors

Exceptions, a missing environment variable, a missing ConfigMap/Secret, a database that is unreachable, or a volume that does not exist.

Cause 1: wrong command

# Dockerfile
CMD ["python3", "app1.py"]      # file is really app.py

Status sequence: ContainerCreating, Error, CrashLoopBackOff, Error again ... Fix the Dockerfile (or the command/args in the Pod spec), build and push a new tag (say v2), update the image in the Deployment and apply. The old Pod terminates and the new one runs.

Cause 2: liveness probe fails

A liveness probe is a health check the kubelet runs: it works like a load balancer's health check. If it fails repeatedly, the kubelet restarts the container, because a hung app can't answer users. (A readiness probe is different: it only decides whether the Pod receives traffic.) Real probes usually call an HTTP endpoint such as /health; a 200 means healthy and a 500 or 404 means unhealthy.

livenessProbe:
  exec:
    command: ["cat", "/tmp/healthy"]   # file never exists
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 3

The container runs, the probe fails, it restarts, repeats. In real life the culprits are a wrong path or port, a probe that starts checking before the app has warmed up (raise initialDelaySeconds, or use a startupProbe), or an app that really is unhealthy.

Cause 3: out of memory

In a shared cluster, you protect neighbours with requests (what the scheduler reserves) and limits (the maximum a container may use). Per-namespace caps are done with a ResourceQuota. If an app leaks memory or the limit is too small, it is killed:

resources:
  requests:
    memory: "64Mi"
    cpu: "100m"
  limits:
    memory: "128Mi"     # container is killed if it goes above this
    cpu: "250m"

CPU is measured in millicores: 1000m is one CPU, so 25m is 1/40 of a CPU. Going over a CPU limit only slows the app; going over a memory limit kills it. Fix: raise the limit if it is simply too low, or report the leak to the developers (with the logs) if the app should not need that much.

Cause 4: errors inside the app or its config

Exceptions at start-up, a required environment variable that is missing or wrong, a Secret or ConfigMap that does not exist, a database that is not reachable. The app logs usually say exactly what happened.

The debug flow

  1. kubectl get pods: see CrashLoopBackOff and the RESTARTS count.
  2. kubectl logs <pod> --previous: the logs of the crashed run. Plain kubectl logs may show the new, empty container. Add -c <container> if the Pod has more than one.
  3. kubectl describe pod <pod>: look at Last State (Reason and Exit Code) and the Events (for example "Liveness probe failed").
  4. Match the evidence to a cause, fix the manifest or image, and apply.
kubectl get pods
kubectl logs my-app-5d9c7-xk2lp --previous
kubectl describe pod my-app-5d9c7-xk2lp

# in describe, look for:
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137

The delay starts at 10s and doubles: 20s, 40s ... and is capped at 5 minutes.

Key takeaways

  • CrashLoopBackOff means the container crashes repeatedly and Kubernetes restarts it with growing delays (10s up to 5 min).
  • It has many causes: wrong command, failing liveness probe, OOMKilled, app or config errors.
  • Debug with kubectl logs --previous and kubectl describe pod (Last State, exit code, Events).
  • Memory over the limit kills the container; CPU over the limit only slows it.
  • Tell a liveness probe (restart me) from a readiness probe (send me traffic) when you diagnose.
