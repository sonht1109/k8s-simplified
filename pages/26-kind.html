Kubernetes in Docker (kind)

kind runs a real Kubernetes cluster inside Docker containers on your laptop. You'll learn why it beats the usual local options, how to create single-node and multi-node clusters in seconds, and how to open your apps from the browser.

Why a local cluster at all?

To practise Kubernetes you need a cluster. Cloud clusters (EKS, AKS, GKE) work, but they cost money and take time to create. Many beginners rent a cloud virtual machine just to run Minikube, and the bill adds up. A local cluster is free, fast, and safe to break.

The problem with the usual choice: Minikube

Minikube is the best-known local option. It has two common modes:

  • VM driver (VirtualBox, HyperKit): Minikube starts a whole virtual machine and puts the control plane and the worker in it ("all-in-one"). A VM wants at least about 2 CPUs and 4 GB of RAM. If your laptop is busy with other things, the VM may fail to start or get killed.
  • Docker driver: Minikube uses a container instead of a VM. Better, but running several clusters or a multi-node cluster at once is clumsy.

What kind does differently

kind stands for Kubernetes in Docker. Each Kubernetes node is simply one Docker container. Inside that container run the kubelet, a container runtime and (on control-plane nodes) the API server, etcd and so on. If you need the pieces explained, see Lesson 2: Architecture.

  • Single-node cluster = 1 container.
  • 1 control plane + 2 workers = 3 containers.
  • A multi-node cluster gets one extra container, a small load balancer in front of the control planes.

Because containers start in seconds and share your laptop's kernel, kind is light. A nine-node cluster can be up in about 30 seconds, and you can keep several clusters side by side (as many as your laptop can handle).

Install and create your first cluster

You need Docker running first, plus kubectl. Then install kind (for example brew install kind on macOS, or download the binary from the kind releases page). On Windows, run Docker Desktop and install kind there; WSL 2 also works.

kind create cluster --name demo
kind get clusters
kubectl config current-context     # kind-demo
kubectl get nodes

kind adds a context called kind-<name> to your kubeconfig and switches to it, so kubectl talks to the new cluster straight away. You can see the "node" as a container:

docker ps | grep -i demo

Multi-node clusters with a config file

A plain kind create cluster gives one node. For more, describe the nodes in a YAML file:

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker
kind create cluster --name multi --config kind-config.yaml
kubectl get nodes

Each - role: line adds one container. Add more worker lines for a bigger cluster, or more control-plane lines to practise a highly available control plane.

Running and reaching apps

Cloud clusters hand out a public address when you create a LoadBalancer Service. A local kind cluster has no cloud to do that, so the address stays pending. The simplest native fix is kubectl port-forward (the details are in Lesson 24):

kubectl create deployment nginx --image=nginx
kubectl get pods
kubectl port-forward pod/<pod-name> 8888:80
# open http://localhost:8888

For a Service of type NodePort or an Ingress on kind, you can publish a node's port to your laptop with extraPortMappings in the config. (Services themselves are covered in Lesson 6 and Lesson 8.)

TipYour own image isn't on a registry? Build it locally and copy it into the cluster: kind load docker-image my-app:1.0 --name demo. Then use that tag in your Pod (and set imagePullPolicy: IfNotPresent).

Clean up

kind delete cluster --name demo
kind delete cluster --name multi

What local clusters are good for, and not

Great for

Learning objects, practising node affinity and taints, scaling, Pod disruption budgets, testing manifests and Helm charts, CI pipelines.

Not great for

Real cloud load balancers, rehearsing a production cluster upgrade, or building admission controllers and operators that need a realistic environment.

Watch outkind is for learning and testing, not production. All nodes share one laptop, so there is no real high availability.

Key takeaways

  • kind = Kubernetes in Docker: every node is a container, so clusters start in seconds and need no VM.
  • kind create cluster --name x makes a cluster and a kind-x kubectl context.
  • Use a kind.x-k8s.io/v1alpha4 config with role: control-plane / worker for multi-node clusters.
  • Run several clusters side by side; delete with kind delete cluster --name x.
  • Use port-forward (or extraPortMappings) to reach apps, and kind load docker-image for local images.
  • Great for learning and testing; not for production or upgrade rehearsals.
