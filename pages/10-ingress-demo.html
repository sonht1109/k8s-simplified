Ingress: Live Demo

Set up Ingress on a local cluster from zero: confirm the app works through a Service, write a host and path rule, install an NGINX ingress controller, and test it. You'll also learn to read the controller's logs and fix the usual "it does nothing" problems.

Why Ingress exists, how controllers work and TLS are covered in Lesson 9. This lesson only walks through the setup. It reuses the Deployment and Service from Lesson 8.

Before you start

You need a running Minikube cluster and the sample app from the previous lesson: a Deployment with Pods labelled app=sample-python-app, listening on 8000 and answering at /demo, exposed by a Service called sample-python-app on port 80.

kubectl get pods
kubectl get svc sample-python-app

If you deleted them, re-create both using Lesson 8. An Ingress can point at a plain ClusterIP Service; it does not need NodePort or LoadBalancer.

Step 1: confirm the Service works first

Always test the layer below before adding a new one. If the Service is broken, Ingress cannot fix it.

curl -L http://$(minikube ip):30007/demo      # only if your Service is NodePort
# or, from inside the cluster:
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- http://sample-python-app/demo

You should see the app's text back. Good: Pods are healthy and the Service finds them.

Step 2: write the Ingress rule

We want requests for foo.bar.com with the path /bar to reach the Service. Create ingress.yaml (start from the example in the Kubernetes docs and change the host, path and service name):

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-example
spec:
  ingressClassName: nginx
  rules:
    - host: foo.bar.com
      http:
        paths:
          - path: /bar
            pathType: Prefix
            backend:
              service:
                name: sample-python-app     # your Service name
                port:
                  number: 80                # the Service port, not 8000
kubectl apply -f ingress.yaml
kubectl get ingress
NAME              CLASS   HOSTS         ADDRESS   PORTS   AGE
ingress-example   nginx   foo.bar.com             80      5s

The ADDRESS column is empty, and requests would do nothing. That is expected: no controller exists yet to read the rule.

Step 3: install an ingress controller

On Minikube the easiest way is the built-in add-on, which installs the NGINX ingress controller:

minikube addons enable ingress

The controller is just a Pod, in its own namespace. Check that it is running:

kubectl get pods -n ingress-nginx
# ingress-nginx-controller-xxxxx   1/1   Running
TipOn a real cluster you install a controller from its own documentation, usually with Helm or a manifest. Search "ingress-nginx install" (or your chosen controller). Do this once per cluster. After that, every new app only needs its own Ingress YAML.

Check the controller noticed your rule

kubectl logs -n ingress-nginx deploy/ingress-nginx-controller | tail
# ... Ignoring ... / successfully synced ... Ingress "default/ingress-example"

A line showing the Ingress was synced means the controller rewrote its nginx.conf for your rule. If the Ingress was created before the controller, it may take a moment, or you can re-apply the file. Now check the address:

kubectl get ingress
# NAME              CLASS   HOSTS         ADDRESS        PORTS
# ingress-example   nginx   foo.bar.com   192.168.64.11  80

The address is filled in, so the controller has picked up the Ingress.

NoteWith Minikube's Docker driver on macOS or Windows, the address may stay empty or unreachable. Run minikube tunnel in a separate terminal and use 127.0.0.1 as the target IP instead.

Step 4: make the hostname resolve

foo.bar.com is not a real domain, so your laptop does not know where it is. In production your company owns a real domain with a DNS record pointing to the load balancer, and this step does not exist. Locally you have two options.

Option A: pretend with /etc/hosts (edit with sudo; remove it later):

echo "$(kubectl get ingress ingress-example -o jsonpath='{.status.loadBalancer.ingress[0].ip}') foo.bar.com" | sudo tee -a /etc/hosts
curl -L http://foo.bar.com/bar

Option B: no file changes, tell curl where to connect:

curl --resolve foo.bar.com:80:$(minikube ip) http://foo.bar.com/bar
# or just set the Host header against the IP:
curl -H "Host: foo.bar.com" http://$(minikube ip)/bar

The rule matches on the Host header, so both ways work. If you call the IP with no host header, you get a 404 from NGINX, which is exactly what the rule is supposed to do.

Watch out about pathsThe rule forwards /bar as-is to your app. Our sample app serves /demo, not /bar, so the app itself may return its own 404. To see the app's page, either set the rule path to /demo or add the NGINX annotation nginx.ingress.kubernetes.io/rewrite-target: /demo. Telling "Ingress 404" from "app 404" matters: the NGINX 404 page says nginx at the bottom.

Step 5: try more rules

Edit ingress.yaml and re-apply to explore what Lesson 9 described:

  • Path-based: add a second path such as /second pointing at another Service.
  • Wildcard host: use host: "*.bar.com", then curl -H "Host: example.bar.com" ... also works. Quote the value.
  • TLS: create a TLS Secret and add a tls: block as shown in Lesson 9.

Pick what you see. The tool suggests the cause and the command to confirm it.

Choose a symptom and press Diagnose.

Debug checklist

  1. kubectl get pods -n ingress-nginx: is the controller running?
  2. kubectl get ingress and kubectl describe ingress ingress-example: is the class right, is there an address, and what backends does it show?
  3. kubectl get endpoints sample-python-app: does the Service have Pod IPs? (Empty means a selector problem, see Lesson 6.)
  4. kubectl logs -n ingress-nginx deploy/ingress-nginx-controller: did the controller pick up the Ingress, and does it log your request?

Clean up

kubectl delete -f ingress.yaml
sudo sed -i '/foo.bar.com/d' /etc/hosts      # if you edited it (use sed -i '' on macOS)
minikube addons disable ingress

Check yourself

You applied an Ingress but ADDRESS is empty and requests fail. What should you check first?
Ingress rules do nothing until a controller with a matching class reads them.
In the Ingress backend, which port number goes in port.number?
The Ingress sends traffic to the Service, so it uses the Service port. The Service then forwards to targetPort.
Why do you edit /etc/hosts in this demo but not in production?
DNS normally maps your real domain to the load balancer. The hosts file fakes that mapping on your laptop.

Key takeaways

  • Test the Service first, then add the Ingress. Ingress points at a Service name and Service port.
  • An Ingress has no effect until a controller is installed; on Minikube: minikube addons enable ingress.
  • A filled ADDRESS and a "synced" log line show the controller picked up your rule.
  • Local testing needs a hosts-file entry or curl --resolve / a Host header; production uses real DNS.
  • Debug in order: controller Pod, Ingress, endpoints, controller logs.
