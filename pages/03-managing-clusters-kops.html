Managing Many Clusters (kOps)

Learning clusters on a laptop is easy. Running real ones means creating, upgrading, changing and deleting them safely, often hundreds of times. You'll learn how Kubernetes is delivered in production and how a tool like kOps manages the whole lifecycle.

This lesson assumes you know the control plane and worker nodes from Lesson 2: Architecture.

Local clusters vs production clusters

Tools such as minikube, kind, k3s and MicroK8s are fantastic for learning and testing. But they are development environments: usually one node, small resources, and no high availability. Their own documentation says not to use them for production.

A DevOps or platform engineer's real job includes the cluster lifecycle:

  1. Create a cluster with multiple control-plane and worker nodes.
  2. Configure it: node sizes, networking, access.
  3. Upgrade Kubernetes versions with little or no downtime (a whole topic, see Lesson 16).
  4. Delete clusters that are no longer needed, to stop paying for them.

(For trying things on your own machine, see Lesson 26: kind.)

Distributions and managed services

Linux is open source, yet most people use a distribution such as Ubuntu, Red Hat or Amazon Linux: the same core with extras and support. Kubernetes works the same way. Companies wrap upstream Kubernetes with installers, a nicer experience and paid support:

  • OpenShift (Red Hat), Rancher, VMware Tanzu
  • Managed cloud services: EKS (AWS), AKS (Azure), GKE (Google)
  • Plain upstream Kubernetes, installed and run by your own team

Under the hood they are all Kubernetes. If you understand the architecture, you understand all of them; the difference is mostly who installs, supports and upgrades it.

Self-managed (e.g. kOps, kubeadm)Managed (EKS, AKS, GKE)

Interview angleNobody will ask about minikube in production. Expect "Which Kubernetes distribution do you use, and who handles upgrades?" Be ready to say how you create, upgrade and delete clusters.

kOps: Kubernetes Operations

Older tools such as kubeadm can create a cluster, but a lot is manual, and upgrades or changes are awkward. kOps (Kubernetes Operations) covers the whole lifecycle: create, update, upgrade, rolling restart, delete. Think "kubectl for clusters." It is most mature on AWS.

Think of it like…A building contractor. You hand over a blueprint (the cluster spec). kOps compares it with what exists, builds or changes what's needed, and can tear it down when you're done.

Hands-on outline

Prerequisites: an AWS account, an admin machine (an EC2 instance works) with kops, kubectl and the AWS CLI installed, and AWS credentials with EC2, S3, IAM and VPC permissions. Running a real cluster costs money, so delete it when finished.

1. Create a state store. kOps needs somewhere to keep each cluster's configuration. It uses an S3 bucket (bucket names are global, so pick a unique one).

aws s3 mb s3://my-kops-state-12345 --region us-east-1
export KOPS_STATE_STORE=s3://my-kops-state-12345

2. Define the cluster. A cluster name ending in .k8s.local uses built-in "gossip" DNS, so you don't need to own a domain.

kops create cluster \
  --name=demo.k8s.local \
  --zones=us-east-1a \
  --node-count=2 \
  --node-size=t3.medium \
  --control-plane-size=t3.medium

This only writes the spec to S3. Nothing is built yet, which lets you review or edit it first (kops edit cluster demo.k8s.local).

3. Build it.

kops update cluster --name demo.k8s.local --yes --admin
kops validate cluster --wait 10m     # waits until nodes are Ready
kubectl get nodes

4. Change or upgrade. Edit the spec (new Kubernetes version, bigger nodes), apply it, then replace machines one at a time:

kops edit cluster demo.k8s.local
kops update cluster --name demo.k8s.local --yes
kops rolling-update cluster --name demo.k8s.local --yes

The rolling update drains and replaces nodes gradually, so apps stay up if they have several replicas.

5. Delete. This removes the machines, load balancers and disks it created.

kops delete cluster --name demo.k8s.local --yes
Watch outFlag names change between kOps versions (for example --master-size became --control-plane-size). Check kops create cluster --help for your version. And always delete practice clusters, since running EC2 instances keep billing.

Managing hundreds of clusters

Large companies have many clusters (per team, per region, per environment). What makes this manageable:

  • Everything is described in files. The spec lives in the state store (and can be exported to Git), so a cluster can be recreated or compared at any time.
  • One tool, same commands for every cluster; only the name changes.
  • Automation. Teams call these commands from CI pipelines or Terraform rather than typing them by hand.
  • Standard versions. Fewer Kubernetes versions across the fleet means fewer surprises and simpler upgrades.
  • Cost control. Developers test in local or short-lived clusters; expensive managed or production clusters are kept for real workloads.

Other options exist (kubeadm, Kubespray, Cluster API, or eksctl for EKS, used in Lesson 17), but the lifecycle questions are always the same.

Check yourself

Why shouldn't minikube be used for production?
Local tools are for learning and testing. Production needs HA control planes, real capacity and proper upgrades.
What is the S3 bucket used for in a kOps setup?
kOps keeps each cluster's desired spec in the state store and builds the cluster from it.
You run kops create cluster without --yes. What happened?
Creation is a two-step process. kops update cluster --yes actually builds it.

Key takeaways

  • Local tools (minikube, kind, k3s) are for learning; production needs a real distribution or managed service.
  • Distributions (OpenShift, Rancher, Tanzu) and managed services (EKS, AKS, GKE) are Kubernetes plus installers and support.
  • The cluster lifecycle is create, configure, upgrade, delete. kOps manages all of it from a spec in a state store.
  • Typical flow: create cluster, update cluster --yes, validate cluster, rolling-update cluster, delete cluster.
  • At scale: describe clusters as files, automate, standardise versions, delete what you don't use.
