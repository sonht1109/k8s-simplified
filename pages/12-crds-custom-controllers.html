Custom Resources & Controllers

Kubernetes ships with objects like Pod, Deployment and Service. But you can teach it brand-new object types and write a program that makes them do real work. That is how tools like Istio and Argo CD plug into Kubernetes.

The problem: built-in objects are not enough

Out of the box Kubernetes knows a fixed list of resource types (Pod, Deployment, Service, ConfigMap, Secret and more). Suppose a project wants to add something Kubernetes does not offer, such as GitOps deployments, a service mesh, or security scanning. It cannot just tell users to "write some YAML" because Kubernetes would reject unknown kinds.

The answer is to extend the Kubernetes API. This takes three pieces that work together.

1. CRD

Custom Resource Definition. The "blueprint". It tells the API server a new type exists and which fields it may have.

2. CR

Custom Resource. One actual object of that new type, written by a user, like one Deployment is an instance of the Deployment type.

3. Custom controller

A program running in the cluster that watches those custom resources and acts on them. Without it, the resource is just stored data.

Think of it like…A CRD is a new form template pinned up at the town office. A custom resource is one filled-in form. The controller is the clerk who reads submitted forms and does the work. Forms without a clerk just pile up.

Comparing with a built-in object

The easiest way to understand all this is to compare it with something you already know.

Built-in (Deployment)Custom (e.g. Istio VirtualService)
Definition of the typeAlready inside KubernetesYou install a CRD
Your objectA Deployment YAMLA custom resource YAML
ValidationAPI server checks it against the built-in schemaAPI server checks it against the CRD's schema
Who acts on itBuilt-in Deployment controllerA custom controller you install

Remember: if you add an unknown field to a Deployment, the API server complains that the field is unknown. A CRD gives custom objects the same kind of checking.

The CRD

A CRD is just a YAML file. Here is a small one that defines a Website type:

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: websites.example.com        # must be plural.group
spec:
  group: example.com
  scope: Namespaced
  names:
    kind: Website
    plural: websites
    singular: website
    shortNames: [ws]
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              image:
                type: string
              replicas:
                type: integer
                minimum: 1

After kubectl apply -f crd.yaml, the API server has a new endpoint and kubectl understands the new type:

kubectl get crds
kubectl api-resources | grep website

The custom resource

Now users can create objects of that type, validated against the schema above:

apiVersion: example.com/v1
kind: Website
metadata:
  name: shop
spec:
  image: nginx:1.27
  replicas: 3
kubectl apply -f shop.yaml
kubectl get websites        # or: kubectl get ws

At this point Kubernetes simply stores the object in etcd. Nothing runs. It is like creating an Ingress with no ingress controller: the rule exists but nobody enforces it.

The controller and the reconcile loop

A controller's whole job is one repeating idea, the reconcile loop:

  1. Observe the desired state (what the custom resource says).
  2. Compare it with the actual state (what really exists in the cluster).
  3. Act to close the gap: create, update or delete things.
  4. Repeat whenever something changes.

For our Website, a controller might create a Deployment with 3 replicas and a Service. If someone deletes the Deployment, the controller notices and creates it again. This is the same pattern the built-in Deployment controller uses to keep Pods running (see Lesson 5).

Who uses this, and who writes it?

Many well-known tools are "CRDs plus a controller": Istio (VirtualService), Argo CD (Application), Prometheus Operator (Lesson 14), cert-manager and more. For a typical DevOps engineer the three steps are:

  1. Install the CRDs (usually from the project's docs, a Helm chart or an operator).
  2. Install the controller, cluster-wide or for specific namespaces.
  3. Teams then create custom resources in the namespaces that need the feature.

Most DevOps engineers use CRDs but do not write them. If you do need to write a controller:

  • Go is the most popular language, because Kubernetes itself is written in Go and its client-go library is mature. Python and Java clients also exist.
  • Under the hood the controller registers watchers for your resource type. Events (created, updated, deleted) go into a work queue, and workers pull items off it and reconcile them.
  • Frameworks hide most of this. controller-runtime, Kubebuilder and the Operator SDK are the common choices.
    • NoteAn operator is a custom controller that encodes human operations knowledge (install, back up, upgrade an app such as a database). Think of it as a controller with a job title.
    Watch outDeleting a CRD deletes every custom resource of that type. Treat CRDs with the same care as a database schema.

    Check yourself

    You applied a custom resource and it shows in kubectl get, but nothing happens. What is most likely missing?
    The CRD already exists (otherwise the apply would have failed). Without a controller, nobody acts on the stored object.
    What does the reconcile loop do?
    Observe, compare, act, repeat. It is the core of every Kubernetes controller.
    What is the difference between a CRD and a CR?
    Like the difference between the Deployment type and one specific Deployment you create.

    Key takeaways

    • CRDs extend the Kubernetes API with new object types, and validate objects of those types.
    • A custom resource is one object of such a type; by itself it is only stored data.
    • A custom controller watches custom resources and makes reality match them via the reconcile loop.
    • Typical flow: install CRD, install controller, create custom resources.
    • Go with controller-runtime, Kubebuilder or Operator SDK is the usual way to build one.
