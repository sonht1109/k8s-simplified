Ingress, TLS & Controllers

Ingress lets many apps share one entry point and routes traffic by hostname and URL path, with HTTPS handled in one place. You'll learn why it was invented, how the Ingress resource and the ingress controller split the work, and the three ways to handle TLS.

Ingress builds on Services. If NodePort, LoadBalancer or kube-proxy are new to you, read Lesson 6 and Lesson 8 first.

Why Services alone are not enough

Services already expose apps, so why does Ingress exist? Teams that moved from virtual machines to Kubernetes hit two problems.

Problem 1: too few features

On VMs, people used load balancers like NGINX, HAProxy or F5 with rich features: path-based and host-based routing, sticky sessions, ratio-based balancing, allow/deny lists, HTTPS, a web application firewall. A Service only offers a simple, even spread of connections (the kind of balancing kube-proxy does), nothing more.

Problem 2: cost

Exposing a Service as LoadBalancer usually gives each one its own cloud load balancer and static public IP, billed separately. With 200 services that is 200 bills. On VMs, you ran one load balancer with one IP and routed to many apps behind it.

Kubernetes' answer is the Ingress: one entry point, many routing rules.

Interview angle"Why Ingress instead of LoadBalancer Services?" Two reasons: (1) advanced HTTP routing and TLS features that Services lack, and (2) one shared load balancer and IP instead of one paid load balancer per Service.

Two pieces: the resource and the controller

Ingress is split in two, on purpose.

  • Ingress resource: a YAML object holding rules, such as "requests for shop.example.com/cart go to the cart Service". It is only a description.
  • Ingress controller: a program running in the cluster that watches Ingress resources and configures a real load balancer to match. Examples: NGINX, HAProxy, Traefik, and cloud-specific ones such as the AWS Load Balancer Controller.

Why split? Kubernetes cannot build in logic for every load balancer on the market. So each vendor writes a controller, and you install the one you want. This follows the same pattern as everywhere else in Kubernetes: a resource describes the wanted state, and a controller makes it real (just like kube-proxy for Services; see Lesson 2).

Watch outAn Ingress resource without a controller does nothing. You can create 100 Ingresses and nothing will happen, because nobody is watching them. Install a controller first; the ADDRESS column of kubectl get ingress stays empty until one picks it up.

Writing an Ingress

A basic Ingress with host and path rules. Note networking.k8s.io/v1 (the old extensions API was removed) and that pathType is required.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: nginx          # which controller should handle this
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /cart
            pathType: Prefix
            backend:
              service:
                name: cart-svc
                port:
                  number: 80
          - path: /pay
            pathType: Prefix
            backend:
              service:
                name: pay-svc
                port:
                  number: 80

Routing options

  • Host-based: shop.example.com and blog.example.com go to different Services, sharing one IP.
  • Path-based: /cart and /pay on the same host go to different Services.
  • Wildcard hosts: *.example.com matches any single subdomain (quote the host in YAML: "*.example.com").
  • Extras via annotations: basic auth, rate limits, redirects and so on, which depend on the controller.

If no rule matches, the controller answers with a 404 from its default backend. A request with the wrong Host header gets that 404 even though the Service is healthy.

Several controllers: IngressClass

A cluster can run more than one controller, for example NGINX for public sites and another for internal tools. The ingressClassName field says which controller owns an Ingress. A controller ignores Ingresses of other classes. If your Ingress never gets an address, a missing or wrong class is a very common reason.

To find out what a controller has actually done, check its Pod logs or generated config. For NGINX, the controller rewrites nginx.conf with a location block for every rule.

TLS: serving HTTPS

TLS encrypts traffic between the client and your server (that is the "S" in HTTPS). With Ingress you can handle it in three ways.

Client to LBEncryptedEncryptedEncrypted
LB to PodEncrypted (untouched)Plain HTTPEncrypted again
Who decryptsOnly the appLoad balancerLB, then app
LB can inspect and route by path?No (TCP level only)YesYes
Load on the appHighLowHigh
Main riskLB cannot filter bad requestsPlain traffic inside your networkMost work, but safest
  • Passthrough: the load balancer just forwards encrypted bytes. Very private, but it cannot see paths, cookies or attacks, so features like path routing or a firewall do not work.
  • Termination: the most common setup. The controller decrypts HTTPS and forwards plain HTTP to Pods. It is simple and fast, but traffic inside is unencrypted, which is a problem if the network is not trusted.
  • Re-encrypt: the controller decrypts, inspects and routes, then encrypts again toward the Pod. Both hops are secure and the LB can still filter, at the cost of the Pod also doing TLS work.
NoteOpenShift calls these "edge", "passthrough" and "re-encrypt" routes. On plain Kubernetes with the NGINX controller, termination is the default; passthrough and re-encrypt are enabled with controller annotations.

TLS termination in Kubernetes

The certificate and key live in a Secret of type kubernetes.io/tls, and the Ingress references it by name. Keeping certificates in a Secret means the Ingress YAML can be stored in Git safely (never commit the key itself).

# 1) a certificate for testing (self-signed)
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout tls.key -out tls.crt \
  -subj "/CN=shop.example.com" -addext "subjectAltName=DNS:shop.example.com"

# 2) store it as a TLS Secret
kubectl create secret tls shop-tls --cert=tls.crt --key=tls.key
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - shop.example.com
      secretName: shop-tls         # must be in the same namespace
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cart-svc
                port:
                  number: 80

A self-signed certificate makes browsers and curl complain ("self-signed certificate"); for testing use curl -k or pass the cert with --cacert tls.crt. In production, use a real certificate, commonly issued automatically by cert-manager with Let's Encrypt. A wildcard certificate (*.example.com) can cover many hosts with a single Secret.

Check yourself

You apply an Ingress YAML on a fresh cluster and the ADDRESS column stays empty. Most likely reason?
The Ingress resource only holds rules. A controller must watch it and configure a load balancer.
Which TLS option lets the load balancer read paths and filter requests, while keeping both hops encrypted?
Re-encrypt decrypts to inspect and route, then encrypts again toward the Pod. Passthrough cannot inspect traffic.
What is one cost-related advantage of Ingress over many LoadBalancer Services?
Each LoadBalancer Service typically gets its own billed cloud load balancer. An Ingress shares one entry point.

Key takeaways

  • Ingress adds host/path routing, TLS and other HTTP features, and lets many apps share one load balancer and IP.
  • The Ingress resource holds rules; the ingress controller (NGINX, HAProxy, Traefik, cloud controllers) makes them real. No controller means nothing happens.
  • Use ingressClassName to pick the controller; pathType and networking.k8s.io/v1 are required.
  • TLS options: passthrough (private, no inspection), termination (simple, fast, plain HTTP inside), re-encrypt (inspection plus encryption both ways).
  • Store certificates in a kubernetes.io/tls Secret and reference it from spec.tls.
