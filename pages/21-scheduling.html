Scheduling: Selectors, Affinity & Taints

By default Kubernetes picks any node with enough room for your Pod. Sometimes you need more control: "only on ARM nodes", "prefer SSD", "keep everything off this node during an upgrade". You will learn four tools for that and how to fix the Pending Pods they can cause.

The scheduler is a control plane component, explained in Lesson 2: Architecture. To practise on several nodes locally, see Lesson 26: kind.

What the scheduler does

When you create a Pod, the kube-scheduler looks at every node, throws out the ones that cannot run it, and picks the best of the rest. The tools in this lesson change that decision. They come in two directions:

The Pod chooses nodes

nodeSelector and node affinity. "I want to run on nodes that look like this."

The node chooses Pods

Taints and tolerations. "I refuse Pods unless they have special permission."

If you set these badly, no node qualifies and the Pod sits in Pending forever. That can mean downtime, so it is worth understanding properly.

Step 1: labels on nodes

Selectors and affinity match against labels, simple key/value tags. Nodes have labels too, and you add your own:

kubectl get nodes --show-labels
kubectl label node worker-2 disktype=ssd
kubectl label node worker-2 disktype-        # trailing dash removes the label

nodeSelector: the simple hard rule

Put a nodeSelector in the Pod spec. The Pod may run only on nodes carrying every listed label.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      nodeSelector:
        disktype: ssd
      containers:
      - name: nginx
        image: nginx:1.25

A real reason to use it: an app built only for ARM processors, or one that needs a node with fast disks or a GPU.

Watch outIf no node has the label, the Pods stay Pending. Run kubectl describe pod <name> and read the Events at the bottom: 
Warning  FailedScheduling  default-scheduler
0/4 nodes are available: 4 node(s) didn't match Pod's node affinity/selector.
Typos (a label on the node that says arm while the Pod asks for arm-worker) are the most common cause. Fix the label or the selector and the Pods start right away.

Node affinity: hard or soft

Node affinity does what nodeSelector does, with more flexibility. It has two modes:

ModeMeaningActs like
requiredDuringSchedulingIgnoredDuringExecutionSchedule only if a node matchesnodeSelector (a hard rule)
preferredDuringSchedulingIgnoredDuringExecutionTry to match; if none, run anywhereA wish (a soft rule)

The long names read as: the rule is applied during scheduling, and ignored during execution, meaning a Pod already running is not moved if labels change later.

spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: disktype
            operator: In
            values: ["ssd"]

For a required rule the shape is slightly different:

      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: kubernetes.io/arch
            operator: In
            values: ["arm64"]

You do not need to memorise this syntax. Copy it from the docs. What matters is the idea: required = must, preferred = nice to have. Operators like In, NotIn, Exists let you write richer rules than a plain label match.

Interview angle"nodeSelector vs node affinity?" Both attract Pods to labelled nodes. nodeSelector is only an exact, hard match. Affinity adds soft preferences and operators, so the scheduler has room to compromise.

Taints: a node says "keep out"

Everything so far is about what a Pod wants. A taint is the reverse: a mark on a node that repels Pods. The classic use is maintenance. Before upgrading a node you want no new Pods landing on it (see Lesson 16).

kubectl taint nodes worker-1 key1=value1:NoSchedule
kubectl taint nodes worker-1 key1=value1:NoSchedule-   # remove it

The format is key=value:effect. There are three effects:

  • NoSchedule: no new Pods are placed here. Pods already running stay.
  • PreferNoSchedule: the scheduler avoids the node but may use it as a last resort. Good for a node that is struggling with CPU or memory problems.
  • NoExecute: no new Pods and existing Pods without a matching toleration are evicted. Use with care; running work stops.

You may have noticed your control plane node never runs your apps. That is a taint: node-role.kubernetes.io/control-plane:NoSchedule.

Tolerations: a Pod gets an exception

A toleration on a Pod says "I am allowed on nodes with this taint". Important or special Pods (monitoring agents, GPU jobs) use it.

spec:
  tolerations:
  - key: "key1"
    operator: "Equal"
    value: "value1"
    effect: "NoSchedule"
Watch outA toleration only permits; it does not attract. A tolerating Pod may land on the tainted node but may equally land elsewhere. To force a Pod onto a dedicated node, combine both: a taint plus toleration to keep others out, and a nodeSelector or affinity to pull the right Pod in.
Think of it like…A taint is a "Staff only" sign on a door. A toleration is a staff badge. A nodeSelector is a note saying "meet me in room 5". The badge lets you in; it does not tell you which room to walk to.

Check yourself

Your Pod has a nodeSelector for gpu=true but no node has that label. What happens?
nodeSelector is a hard rule. With no matching node the Pod waits in Pending, and kubectl describe pod shows why.
A Pod has a toleration for a taint on node X. Where will it run?
Tolerations permit; they do not attract. Add a nodeSelector or affinity to pin the Pod to the tainted node.
Which taint effect also evicts Pods that are already running on the node?
NoExecute evicts running Pods that do not tolerate the taint. NoSchedule only affects new Pods.

Key takeaways

  • nodeSelector and node affinity let a Pod pick nodes by label; taints let a node repel Pods.
  • nodeSelector and required affinity are hard rules; preferred affinity is a soft wish.
  • Taint effects: NoSchedule, PreferNoSchedule, NoExecute (which also evicts).
  • A toleration permits a Pod onto a tainted node but does not pull it there.
  • Pending Pods? Run kubectl describe pod and read the FailedScheduling event.
