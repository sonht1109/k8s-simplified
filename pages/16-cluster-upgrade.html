Upgrading a Cluster in Production

Kubernetes ships a new version about every three months, and only the latest three are supported. Upgrading a live cluster without downtime is a routine DevOps job and a favourite interview topic. You will learn the checks to do first, the order of the upgrade, and how to prove it worked.

New to the pieces of a cluster? The control plane and worker nodes are explained in Lesson 2: Architecture. Managing many clusters is covered in Lesson 3.

Why you must upgrade

  • Kubernetes releases a new minor version (1.30, 1.31, 1.32 ...) roughly every three months.
  • Only the latest three minor versions get security fixes. Cloud providers sometimes extend support a little, but plan on the latest three.
  • A company usually runs several clusters (dev, QA/staging, pre-production, production), so you will repeat this often.

The examples here use AWS EKS, a managed cluster. The steps are almost the same on AKS, GKE and self-managed clusters.

Watch out: no way backA cluster upgrade is irreversible. If you go from 1.30 to 1.31 and something breaks, you cannot downgrade the cluster. Your only way back is a fresh cluster. That is why almost all of the work happens before you press the button.

Part 1: Prerequisites (the real work)

In production, the prep takes days. The upgrade command itself takes minutes.

  1. Optional: cordon the nodes. "Cordon" means mark a node unschedulable so no new Pods land on it. Teams that want extra safety announce a 1-2 hour window with no new deployments. Running apps are not touched. This is not mandatory.
  2. Read the release notes for the version you are moving to. Look for removed or deprecated APIs and changed behaviour. Example: Ingress once lived in the extensions/v1beta1 API group and moved to networking.k8s.io. A cluster that dropped the old group would stop honouring Ingress objects still written the old way.
  3. Test in lower environments first. Upgrade dev, then staging, then pre-production. Wait one to two weeks. Only then touch production.
  4. Make versions match. The nodes must be on the same version as the control plane before you upgrade the control plane. If the control plane is 1.30 and nodes are 1.29, upgrade the nodes to 1.30 first. The kubelet (the agent on each node) must be compatible with the control plane too.
  5. Check add-ons. If you run the Cluster Autoscaler, its version must be compatible with the new control plane version. Helm, Argo CD, Prometheus and friends are just controllers and Pods, so verify them in lower environments.
  6. Free IP addresses. On EKS, keep at least five free IP addresses in the subnets you gave the cluster. Upgrades temporarily need extra network addresses.
  7. Know your cluster. Know which controllers, add-ons and networking setup you have. Otherwise the release notes will not mean anything to you.
Backups and a rollback planBecause you cannot downgrade, "rollback" means being ready to recover. Keep your manifests in Git, back up anything stateful (databases, persistent volumes, and etcd if you run it yourself), and know how you would rebuild the cluster and redeploy. On managed services the provider backs up the control plane for you, but your own data and YAML are still your job.

Part 2: The upgrade order

Always go in the same order, one minor version at a time (you cannot skip from 1.29 straight to 1.31):

Step 1: Control plane

A managed control plane (EKS, AKS, GKE) means the provider keeps it highly available, secure and scaled. It does not mean it upgrades itself. You still ask for the upgrade, in the console, the cloud CLI or a tool like eksctl:

eksctl upgrade cluster --name demo --region us-east-1 --version 1.31 --approve

Before you run it, check the console's upgrade insights (on EKS). It flags add-ons or APIs outside the compatibility range. When it finishes, the control plane runs the new version but your nodes do not yet.

Step 2: Nodes (the data plane)

This is where you need to be careful. How you do it depends on how nodes were created:

Managed node group

Choose a rolling update. The service replaces nodes one at a time, so Pods are moved off a node before it is replaced. Best for large clusters (100+ nodes). Use the "force" option only when a PodDisruptionBudget blocks the drain.

Self-managed nodes

You do it yourself: cordon, drain, replace. For small clusters you can instead create a new node group on the new version, then delete the old one. Custom AMIs or launch templates are your job to rebuild.

Draining one node by hand looks like this:

kubectl cordon node-1                  # stop new Pods landing here
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
# replace or upgrade the node, then:
kubectl uncordon node-1                # allow scheduling again

drain evicts the Pods so their Deployment recreates them on other nodes. That is how the rolling behaviour of Deployments keeps your app up while nodes change.

Note: PodDisruptionBudgetsA PodDisruptionBudget (PDB) says "always keep at least N replicas running". A drain respects it, which keeps the app safe but can make a drain wait. That is the one case where a forced update is considered.

Step 3: Add-ons

Cluster add-ons such as kube-proxy, the VPC CNI network plugin and CoreDNS have their own versions. Upgrade each to a version compatible with the new cluster version. On EKS this is a button or one command per add-on and usually goes smoothly.

How do you know it worked?

Do not check tools one by one. Run your end-to-end (functional/regression) test suite against the upgraded cluster. If real user journeys still pass, the upgrade is healthy. Also check that all nodes show Ready and the new version:

kubectl get nodes
kubectl version
kubectl get pods -A
Try it: upgrade pre-flight check

Answer in this order: read the release notes, test in lower environments, make sure nodes and kubelet match the control plane, check add-on compatibility and free IPs; then upgrade control plane, rolling-update the nodes, upgrade add-ons, and run end-to-end tests. Check yourself

What is the correct order for a cluster upgrade?
The control plane goes first, then the nodes are brought to the same version, then the add-ons. Finish by running tests.
After upgrading 1.30 to 1.31 you find a serious problem. What can you do?
Cluster upgrades are irreversible. This is why testing in lower environments and having backups matter so much.
Your control plane is 1.30 and your nodes are 1.29. You want 1.31. What first?
Nodes must match the control plane before the next upgrade, and you move one minor version at a time.

Key takeaways

  • Only the latest three Kubernetes versions are supported, so upgrading is a regular duty.
  • Upgrades are irreversible. Prevent problems with release notes, lower-environment tests (1-2 weeks) and backups.
  • Nodes and kubelet must match the control plane first; autoscaler and add-ons must be compatible; keep 5 free IPs (EKS).
  • Order: control plane, nodes, add-ons, one minor version at a time.
  • "Managed" control plane means the provider runs it, not that it upgrades itself.
  • Use cordon/drain or rolling node updates, and verify with end-to-end tests.
