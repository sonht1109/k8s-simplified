Headless Services

A normal Service hides your Pods behind one IP and spreads requests between them. Sometimes that is exactly what you don't want. A headless Service gives each Pod its own stable DNS name instead, which is what databases and other stateful apps need.

Need a refresher on what a Service does, with selectors, endpoints and load balancing? See Lesson 6: Services. StatefulSets and volumes are covered in Lesson 22.

Quick recap: why normal Services work so well

Pod IPs change whenever a Pod is replaced. A normal Service (type ClusterIP) gives clients one stable virtual IP and DNS name. It finds Pods by label selector, and kube-proxy forwards each request to one of the healthy Pods, roughly round-robin. For stateless apps (web servers, APIs) any replica can answer, so this is perfect.

The problem: stateful apps

Imagine a backend talking to a database with two replicas, mysql-0 and mysql-1, each with its own volume.

  1. Request 1: "add a new employee". The Service sends it to mysql-0, which stores it on its volume.
  2. Request 2: "list all employees". The Service sends it to mysql-1, which never saw the new employee.

The user sees missing data. The replicas are not interchangeable, so the Service's load balancing becomes a bug. Clients need to say which replica they want. Examples: "write to the primary", "read from replica 1", "never send traffic to the backup node".

What a headless Service is

A headless Service is a Service with clusterIP: None. Kubernetes then gives it no virtual IP and does no proxying or load balancing. All it does is publish DNS records so that clients can find the Pods directly.

Think of it like…A normal Service is a company's reception desk: you call one number and get whoever is free. A headless Service is the staff directory: it lists everyone's direct line, and you choose who to call.

The YAML

The only difference from a normal Service is clusterIP: None. The selector still matches the Pods by label.

apiVersion: v1
kind: Service
metadata:
  name: mydb-headless
spec:
  clusterIP: None
  selector:
    app: mysql
  ports:
  - port: 3306
    name: mysql

Then a StatefulSet whose serviceName points at that Service. That link is what gives each Pod its own DNS name.

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql-stateful
spec:
  serviceName: mydb-headless
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        env:
        - name: MYSQL_ROOT_PASSWORD
          value: "demo-only-password"   # use a Secret in real life
        ports:
        - containerPort: 3306
TipCreate the headless Service first, then the StatefulSet. DNS is the whole point, so the Service should exist when the Pods start.

The DNS names you get

Each StatefulSet Pod gets a predictable name (mysql-stateful-0, -1, -2), and the headless Service publishes a DNS record for each:

<pod-name>.<service-name>.<namespace>.svc.cluster.local

mysql-stateful-0.mydb-headless.default.svc.cluster.local
mysql-stateful-1.mydb-headless.default.svc.cluster.local

The Pod's IP can change when it is recreated, but the name keeps pointing to the right replica. Your backend can safely put mysql-stateful-0.mydb-headless... in a ConfigMap.

The Service name alone (mydb-headless.default.svc.cluster.local) returns the IPs of all ready Pods, which is useful for clients that discover every member themselves, as in database clusters.

Try it on a cluster

kubectl apply -f headless-svc.yaml
kubectl apply -f statefulset.yaml
kubectl get svc            # CLUSTER-IP shows None
kubectl get pods -o wide   # note the IP of mysql-stateful-0

kubectl run -it --rm dns-test --image=busybox:1.36 --restart=Never -- \
  nslookup mysql-stateful-0.mydb-headless.default.svc.cluster.local

kubectl delete pod mysql-stateful-0
# wait for it to come back, then run the nslookup again:
# same name, new IP

The CLUSTER-IP column showing None confirms it is headless, and the repeated lookup shows the DNS name following the Pod through a restart.

Check yourself

Which field makes a Service headless?
Setting clusterIP: None tells Kubernetes not to allocate a virtual IP or do proxying.
Why is a normal Service a poor fit for a two-replica database where each replica has its own storage?
Round-robin treats replicas as interchangeable, but database replicas hold different data and roles.
What happens to mysql-stateful-0.mydb-headless... when the Pod is deleted and recreated with a new IP?
StatefulSet Pods keep their identity, so the DNS name keeps pointing to the replacement Pod.

Key takeaways

  • Normal Services proxy and load balance, which suits stateless apps but not replicas with different data.
  • A headless Service has clusterIP: None: no proxy, only DNS records pointing at Pods.
  • With a StatefulSet (serviceName set), each Pod gets pod.service.namespace.svc.cluster.local.
  • Names stay stable while Pod IPs change.
  • Create the headless Service before the StatefulSet.
