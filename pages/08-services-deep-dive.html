Services Deep Dive: Hands-On

Build a Deployment, then put each kind of Service in front of it: ClusterIP, NodePort, LoadBalancer and ExternalName. You'll learn what port, targetPort and nodePort mean, and break discovery on purpose to see how selectors work.

Why Services exist (stable IPs, discovery, load balancing) is explained in Lesson 6. Deployments are covered in Lesson 5. This lesson is the practical follow-up.

Step 1: a Deployment with two replicas

The demo uses a small web app that listens on port 8000 and answers at the path /demo. You can use any app; just know which port it listens on (look in its Dockerfile for EXPOSE or the start command). We use two replicas so we can see load balancing.

Build the image. On Minikube, build it inside the cluster's Docker so the cluster can find it:

eval $(minikube docker-env)
docker build -t sample-python-app:v1 .

Then write deployment.yaml. You never need to memorise it; copy the example from the Kubernetes docs and change the name, labels, replicas, image and port.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-python-app
  labels:
    app: sample-python-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: sample-python-app
  template:
    metadata:
      labels:
        app: sample-python-app      # Services will look for this
    spec:
      containers:
        - name: python-app
          image: sample-python-app:v1
          imagePullPolicy: IfNotPresent   # use the locally built image
          ports:
            - containerPort: 8000
kubectl apply -f deployment.yaml
kubectl get deploy
kubectl get pods -o wide

The -o wide output shows each Pod's IP. Delete one Pod with kubectl delete pod <name> and list again: the ReplicaSet creates a replacement, usually with a different IP. That is the problem Services solve.

These Pod IPs only work inside the cluster. On Minikube you can test with minikube ssh and then curl -L http://<pod-ip>:8000/demo (the -L follows the app's redirect). From your own laptop, the same URL fails.

Step 2: the three port fields

Before writing a Service, get these three straight. Mixing them up is the number one beginner mistake.

FieldMeaningIn our demo
targetPortThe port the container listens on. Where the Service sends traffic.8000
portThe port the Service itself listens on, on its ClusterIP.80
nodePortThe port opened on every node (NodePort and LoadBalancer types only). Range 30000-32767.30007
Try it: trace a request through the ports

Change the numbers and see the path. Try a nodePort outside 30000-32767, or use Break it to see what a wrong targetPort does.

Press Trace request.

Step 3: ClusterIP (the default)

With no type, you get ClusterIP: a stable virtual IP that works only inside the cluster. It gives you discovery and load balancing, and it is what Pods use to call each other.

apiVersion: v1
kind: Service
metadata:
  name: sample-python-app
spec:
  selector:
    app: sample-python-app      # copy from the Pod TEMPLATE labels
  ports:
    - port: 80
      targetPort: 8000

Or generate it with a command: kubectl expose deployment sample-python-app --port=80 --target-port=8000.

Step 4: NodePort

Add type: NodePort and a nodePort to open the same port on every node. Anyone who can reach a node's IP (everyone in your company network or VPC) can now use the app.

apiVersion: v1
kind: Service
metadata:
  name: sample-python-app
spec:
  type: NodePort
  selector:
    app: sample-python-app
  ports:
    - port: 80
      targetPort: 8000
      nodePort: 30007           # optional; Kubernetes picks one if omitted
kubectl apply -f service.yaml
kubectl get svc
# NAME                TYPE       CLUSTER-IP     PORT(S)        AGE
# sample-python-app   NodePort   10.96.121.5    80:30007/TCP   5s

minikube ip                                  # node IP
curl -L http://$(minikube ip):30007/demo     # from your laptop

Notice 80:30007/TCP: Service port 80 is mapped to node port 30007. A NodePort Service also has a ClusterIP, so the inside-the-cluster address still works. Use the node port number, not 80, when calling a node IP. People outside your network still cannot reach it, because they cannot reach your nodes.

TipOn Minikube with some drivers the node IP is not directly reachable. Run minikube service sample-python-app --url to get a working URL.

Step 5: LoadBalancer

Change the type to LoadBalancer (edit the file and re-apply, or kubectl edit svc sample-python-app). On a cloud cluster (EKS, AKS, GKE), the cloud controller manager creates a real load balancer and fills in the external address after a minute or two.

kubectl get svc sample-python-app
# NAME                TYPE           EXTERNAL-IP
# sample-python-app   LoadBalancer   a1b2c3.elb.amazonaws.com    (on AWS)

Anyone on the internet can now use that address. On Minikube or other local clusters nobody provides the load balancer, so EXTERNAL-IP stays <pending>. Run minikube tunnel in a second terminal to simulate it, or install MetalLB on bare-metal clusters.

Watch outEvery LoadBalancer Service usually creates its own cloud load balancer and public IP, and you pay for each. For many HTTP apps, a single Ingress is the cheaper pattern.

ExternalName: a DNS alias

The fourth type does not select Pods at all. An ExternalName Service makes an outside hostname look like an in-cluster Service name. Pods call my-db, and cluster DNS answers with a CNAME to the real address. Handy when a database lives outside the cluster and you may move it later.

apiVersion: v1
kind: Service
metadata:
  name: my-db
spec:
  type: ExternalName
  externalName: db.example.com

Experiment: break service discovery

Proof that Services find Pods by label only:

  1. Edit the Service selector to a typo, for example app: sample-python-ap, and apply it.
  2. Run kubectl get endpoints sample-python-app. The list is empty, and curl now fails to connect, even though both Pods are healthy.
  3. Fix the selector and apply again. Within a few seconds kube-proxy updates the rules and the app answers again.

Tip: always create Services with kubectl apply -f so you can edit the file and re-apply later.

Experiment: see the load balancing

Send several requests through the Service, then look at which Pod logged each one:

for i in 1 2 3 4 5 6; do curl -s -o /dev/null http://$(minikube ip):30007/demo; done
kubectl logs -l app=sample-python-app --prefix --tail=10

The --prefix flag adds the Pod name to each log line. You will see both Pods handled requests. (A traffic viewer such as Kubeshark can also draw this flow, showing each request going from the Service to one of the two Pod IPs.)

Interview angle"What is the difference between port, targetPort and nodePort?" Service port = where the Service listens; targetPort = the container's port; nodePort = the port on every node (30000-32767). Be ready to say that a wrong targetPort gives "connection refused" while a wrong selector gives an empty endpoint list.

Check yourself

Your container listens on 8000. The Service has port: 80. What should targetPort be?
targetPort is always the port the container itself listens on.
On Minikube, your LoadBalancer Service shows EXTERNAL-IP <pending>. Why?
The cloud controller manager creates load balancers on cloud platforms. A local cluster has nothing to do it, so the address stays pending.
Which Service type has no selector and just returns a DNS alias to an outside hostname?
ExternalName maps a Service name to an external DNS name using a CNAME record.

Key takeaways

  • port is the Service's port, targetPort is the container's port, nodePort is the node's port (30000-32767).
  • ClusterIP is internal, NodePort adds a port on every node, LoadBalancer adds a cloud load balancer. Each type includes the one before it.
  • The Service selector must match the Pod template labels; check with kubectl get endpoints.
  • LoadBalancer needs a cloud provider (or MetalLB / minikube tunnel locally).
  • ExternalName is a DNS alias for something outside the cluster.
