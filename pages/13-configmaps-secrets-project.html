Project: ConfigMaps & Secrets

An app needs settings (a database port, a username, a password). Hard-coding them into the image is a bad idea. In this hands-on project you will store them in ConfigMaps and Secrets, feed them to a running app, and see what happens when the values change.

Why not hard-code configuration?

Picture a back-end app that talks to a database. It needs the database port, username, password, connection type and so on. If these are baked into the code or the container image:

  • Changing a value means rebuilding and redeploying the image.
  • You may not even know the values when you build the image; they might come later from a database admin.
  • The same image cannot be used in dev, staging and production.

The general rule, outside Kubernetes too, is to keep the app generic and give it settings from the outside, as environment variables or as files. Kubernetes provides two objects for this.

ConfigMap

Stores non-sensitive settings as key-value pairs or whole files: ports, feature flags, config files.

Secret

Stores sensitive values: passwords, tokens, certificates. Handled with extra care by Kubernetes.

Step 1: create a ConfigMap

Start with a ConfigMap holding the database port.

apiVersion: v1
kind: ConfigMap
metadata:
  name: test-cm
data:
  db-port: "3306"
kubectl apply -f cm.yaml
kubectl get cm
kubectl describe cm test-cm

Prefer kubectl apply over create because you can re-run it safely after editing the file. A one-liner also works, which is handy for quick tests:

kubectl create configmap test-cm --from-literal=db-port=3306

Step 2: use it as an environment variable

Take a Deployment (see Lesson 5) and add an env entry to the container that reads from the ConfigMap:

spec:
  containers:
  - name: app
    image: nginx
    env:
    - name: DB_PORT
      valueFrom:
        configMapKeyRef:
          name: test-cm
          key: db-port

Apply it, then look inside a Pod:

kubectl apply -f deployment.yaml
kubectl get pods
kubectl exec -it <pod-name> -- env | grep DB
# DB_PORT=3306

The app can now read DB_PORT like any environment variable (for Python, os.environ["DB_PORT"]).

TipIf the YAML is rejected with an error such as "unknown field", check the spelling against the docs. The correct field is configMapKeyRef, not configMapRef (which belongs to a different place, envFrom). Mistakes like this are normal; the API server's message tells you exactly which field it did not understand.

The catch: environment variables do not update

Now edit the ConfigMap and change the port to 3307, then apply it. Exec into the Pod again: DB_PORT is still 3306. A container's environment is set when it starts and cannot change while it runs. Your app would keep using the old port and fail to connect.

Restarting the Pods fixes it (kubectl rollout restart deployment/<name>), but in production you want to avoid needless restarts. That is where volumes help.

Step 3: mount it as a volume

A ConfigMap can be mounted as a volume. Each key becomes a file, and its content is the value. Replace the env block with:

spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: db-connection
      mountPath: /opt
  volumes:
  - name: db-connection
    configMap:
      name: test-cm

Two things happen: volumes (at Pod level) declares where the data comes from, and volumeMounts (inside the container) says where to put it. Check the result:

kubectl exec -it <pod-name> -- cat /opt/db-port
# 3306

Now change the value in the ConfigMap and apply it. Do not restart anything. After a short delay (typically up to a minute) the file inside the running Pod shows the new value:

kubectl exec -it <pod-name> -- cat /opt/db-port
# 3307
Watch outThe file updates, but your app must re-read it to notice. Also, files mounted with subPath are not updated automatically.

Step 4: Secrets

Secrets work the same way as ConfigMaps (same env and volume patterns), but are meant for sensitive data. Create one from the command line:

kubectl create secret generic test-secret --from-literal=db-password=S3cr3t

Or write it in YAML. Use stringData to type plain text and let Kubernetes encode it:

apiVersion: v1
kind: Secret
metadata:
  name: test-secret
type: Opaque
stringData:
  db-password: S3cr3t

Use it in a Pod exactly like the ConfigMap, swapping the key names:

env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: test-secret
      key: db-password
# or as a volume
volumes:
- name: creds
  secret:
    secretName: test-secret

There are other Secret types too, for example kubernetes.io/tls for certificates (used by Ingress TLS) and generic/Opaque for plain key-value data.

The base64 caveat

Look at a Secret with kubectl get secret test-secret -o yaml and the value looks scrambled. It is only base64 encoded, which is a way to write bytes as text, not encryption. Anyone can decode it:

echo 'UzNjcjN0' | base64 --decode
# S3cr3t
Try it: base64 is not secret

Type a password to see its base64 form, or paste a base64 value from a Secret to decode it.

So how are Secrets any safer?

On their own, Secrets are not very secret. They are safer only if you add protections:

  • Encrypt at rest. By default the API server stores Secrets in etcd with only base64. You can enable encryption of etcd data (or use an external KMS), so a stolen etcd copy is unreadable. Managed clusters often offer this as a setting.
  • Lock down access with RBAC. Anyone who can get secrets can read them. Give that permission to as few people as possible (least privilege). See Lesson 11: RBAC.
  • Use external tools such as HashiCorp Vault or Sealed Secrets if you need stronger protection, and never commit real Secret YAML to Git.

That is the interview answer to "ConfigMap vs Secret": same mechanics, but Secrets are for sensitive data and can be encrypted and access-controlled separately. More hardening is in Lesson 23.

PracticeRepeat this project with a Secret holding db-password: first consume it as an env variable with secretKeyRef, then as a volume, and compare how each reacts when you change the value.

Check yourself

You change a ConfigMap that a Pod reads through an environment variable. What happens to the running Pod?
Environment variables are set at container start. Mounted volumes, in contrast, are refreshed.
Is base64 in a Secret a good form of protection?
Base64 is trivially reversible. Real protection comes from encrypting etcd and restricting who can read Secrets.
Where do volumes and volumeMounts go in a Pod spec?
The Pod declares the volume; each container says where to mount it.

Key takeaways

  • Keep configuration out of images: ConfigMap for non-sensitive data, Secret for sensitive data.
  • Consume either as environment variables (configMapKeyRef / secretKeyRef) or as mounted files.
  • Env variables are fixed at start; mounted volumes refresh automatically after a short delay (not with subPath).
  • Secret values are base64-encoded, not encrypted. Anyone can decode them.
  • Protect Secrets with encryption at rest, tight RBAC and never storing them in Git.
