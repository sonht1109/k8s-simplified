Securing Kubernetes Like a Pro

A default cluster is built for convenience, not safety. This lesson is the DevSecOps checklist: seven layers of protection, from the API server at the front door to the container images you run, with the commands and YAML to apply each one.

Architecture terms (API server, etcd, kubelet) come from Lesson 2. RBAC is covered fully in Lesson 11, Secrets in Lesson 13, and monitoring in Lesson 14.

Security in layers

No single control makes a cluster safe. Good teams use defense in depth: if an attacker gets past one layer, the next one still stops them. Here are the layers, roughly from the outside in.

1. Secure the API server

Every request, from kubectl, a CI job or an attacker, goes through the API server. It is the front door, so protect it first.

  • Use TLS. Like the padlock in your browser for https, TLS encrypts traffic and proves the server is genuine. The API server is configured with a certificate, a private key and a client CA. On kubeadm-style clusters it is a static Pod defined in /etc/kubernetes/manifests/kube-apiserver.yaml with flags: 
    --tls-cert-file=/etc/kubernetes/pki/apiserver.crt
--tls-private-key-file=/etc/kubernetes/pki/apiserver.key
--client-ca-file=/etc/kubernetes/pki/ca.crt
    Certificates can be self-signed or issued by a certificate authority. Managed services (EKS, AKS, GKE) do this for you.
  • Restrict who reaches it. Disable anonymous access (--anonymous-auth=false), limit network access to the API endpoint (firewall or private endpoint), and use RBAC for authorization.
  • Keep an audit trail. Audit logging (--audit-policy-file, --audit-log-path) records who did what and when, so you can investigate later.
TipProduction clusters use three control plane nodes for high availability. If one fails, the API server keeps answering from the others.

2. RBAC: least privilege

Authentication proves who you are; RBAC (role-based access control) decides what you may do. With thousands of users and many Pods using the API (CI tools, operators), give each only what it needs: a Role listing allowed verbs on resources, and a binding that attaches it to a user or service account. A tester should not be able to delete production Deployments. Details and commands are in Lesson 11. RBAC applies to all resources, not just the API server.

3. Network policies

By default every Pod can talk to every other Pod, even across namespaces. If a front-end Pod is compromised, it could reach your user database. A NetworkPolicy is a firewall rule for Pods. A common start is "deny all incoming traffic in this namespace", then allow only what is needed:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: finance
spec:
  podSelector: {}        # every Pod in the namespace
  policyTypes:
  - Ingress              # no ingress rules listed = nothing allowed in
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
  namespace: finance
spec:
  podSelector:
    matchLabels:
      app: db
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api
    ports:
    - protocol: TCP
      port: 5432
Watch outNetworkPolicies are enforced by the cluster's network plugin (CNI). Plugins such as Calico or Cilium enforce them; some simple setups silently ignore them. Test that traffic is really blocked.

4. Pod security

A container running as root is a risk: if it is hacked, the attacker has strong powers inside. Set safe defaults in the Pod spec:

spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: myapp:1.4.2
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]

To enforce this across a namespace, use the built-in Pod Security Admission, which rejects Pods that break a standard (privileged, baseline, restricted):

kubectl label namespace finance pod-security.kubernetes.io/enforce=restricted

5. Secure container images

Your cluster is only as safe as the images it runs. An image may contain an old base OS or a library with a known vulnerability (a bug attackers can exploit). Check images before they reach production, ideally in your CI pipeline:

trivy image myrepo/myapp:1.4.2 --severity HIGH,CRITICAL
# similar tools: Snyk, Clair, Quay's scanner
  • Pin a specific base image version instead of latest; prefer small bases (slim, distroless).
  • If scanning finds problems, update the base image or the vulnerable package, rebuild and rescan.
  • Pull only from registries you trust; fail the pipeline on critical findings.

6. Encrypt secrets in etcd

Every Kubernetes object, including Secrets (passwords, tokens, keys), is stored in etcd. You may have locked Secrets down with RBAC, but an attacker who reaches etcd, or a backup of it, can read them all. Worse, a Secret is only base64-encoded by default, which is not encryption. Encryption at rest makes the API server encrypt data before writing it:

apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources: ["secrets"]
  providers:
  - aescbc:
      keys:
      - name: key1
        secret: <base64-encoded 32-byte key>
  - identity: {}      # lets it still read old, unencrypted data

Point the API server at it with --encryption-provider-config=/path/to/file. Existing Secrets are only encrypted when rewritten (kubectl get secrets -A -o json | kubectl replace -f -). Managed clouds usually offer this as a setting using their key service.

7. Monitor, then upgrade

Even with every control in place you need to notice trouble. Imagine someone opens a shell in a Pod and reads /etc/shadow. Runtime security tools such as Falco or Sysdig run as a DaemonSet (one Pod on every node), watch system calls, and alert on suspicious behaviour like a shell in a container or a root process. Combine this with the metrics tooling in Lesson 14.

Finally, upgrade often. Old Kubernetes versions stop getting security fixes. The same goes for node operating systems and add-ons. The procedure is in Lesson 16.

Key takeaways

  • Everything goes through the API server: use TLS, restrict access and enable audit logs.
  • Apply least privilege with RBAC and run Pods as non-root with Pod Security settings.
  • Pods talk freely by default; NetworkPolicies restrict traffic.
  • Scan images in CI and encrypt Secrets in etcd; base64 is not encryption.
  • Watch runtime behaviour (Falco, Sysdig) and upgrade regularly.
